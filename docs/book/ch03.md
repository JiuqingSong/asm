# 第 3 章：第一条指令

> 试验稿 pilot-1。前两章的必要准备在下面补齐，因此可以单独阅读。本章源码是 `teaching/ch03`，共享宿主和观察工具在 `teaching/shared`；没有引用第 4 章或完整项目的 CPU。

## 1. 本章要做什么

先不安装 DOS，不显示字符，不接键盘。我们的目标只有一个：

> 把 `B8 34 12 BB CD AB F4` 装入内存，让 CPU 得到 AX=1234h、BX=ABCDh，然后停下来。

这七个字节不是 TypeScript 程序，而是我们要执行的 8086 机器码。TypeScript 程序负责模拟执行这些字节的 CPU。

如果你写过一点程序，可能已经熟悉“变量赋值”和“调用函数”，也知道程序最后会被机器执行。但这里往往还缺少一段联系：源码中的一句话，究竟怎样成为机器能够执行的动作？我们通常把这段过程交给编译器、操作系统和处理器，结果是程序能跑，却不容易说清其中每一步是谁完成的。

本章把这段联系缩小到最容易观察的程度。先不讨论编译器怎样优化代码，也不讨论操作系统怎样建立进程；只准备几个指令字节和一小块机器状态，然后亲眼看它们之间发生的变化。这样的简化不是说其他层不重要，而是暂时排除干扰：当 AX 从零变成 1234h 时，我们能够确定，变化来自 CPU 对这条指令的执行，而不是某个系统服务替我们做了赋值。

还要注意，“没有显示字符”不等于“没有运行”。屏幕上的输出只是机器工作的一种外部结果。寄存器和内存状态发生符合规则的改变，本身就是执行的结果。我们从这里出发，之后再把这些结果接到显示、磁盘和输入设备上。

本章结束时，机器具有：

| 已实现 | 未实现 |
|---|---|
| 64KB 平坦内存、8 个 16 位通用寄存器、16 位 IP | CS:IP 分段寻址、数据访存指令、ModR/M |
| `B8`～`BF`：MOV r16, imm16 | 其他 MOV 编码、8 位寄存器指令 |
| `F4`：HLT | 中断、异常、唤醒、设备时钟 |
| 宿主装载、单步、只读观察 | BIOS、DOS、显示设备、CALL/RET、分支 |

这不是一台已经兼容全部 8086 程序的机器，而是一块行为范围清楚、可以继续扩展的 CPU 核心。

第一次读这一章，不必把每个操作码记住。更值得记住的是一条关系：**机器当前保存着状态，程序提供下一步的指令，CPU 根据固定规则把旧状态变成新状态。** 后面增加算术、跳转甚至分页时，机器会复杂得多，但这个关系不会消失。

## 2. 谁提供了什么

我们很容易把“这件事发生在 CPU 执行时”误认为“这件事全部由 CPU 提供”。例如，处理器执行一个文件读取程序，但文件名格式、目录结构和打开文件的接口并不是加法器或译码器自带的。本章先用最简单的 MOV 建立这种区分，避免以后把所有能运行的功能都笼统归给 CPU。

可以把 CPU 的指令规则理解成双方约定的接口：程序制造者按照规则安排字节，CPU 按照规则解释字节。这里固定的是解释方法，不固定的是每次输入的内容。类似一个函数的实现不会因为调用参数不同而变成另一个函数，MOV 的执行机制也不会因为立即数从 1234h 改成 3412h 而改变。

| 内容 | 提供者 | 本章中的位置 |
|---|---|---|
| B8 的含义、16 位值、低字节在前、MOV 不修改标志 | 8086 指令集规范 | CPU 核心实现这些规则 |
| B8 34 12 等字节、指令排列顺序 | 应用程序 | 实验中的机器码数组 |
| 把程序放到地址 0、清零寄存器、设置初始 IP | 宿主装载器 | 网页调用 `cpu.load()` |
| 读指令、译码、更新寄存器和 IP | 被模拟 CPU | `CPU.step()` |
| 按钮、文本框、寄存器展示 | 浏览器宿主与观察模块 | 不属于客体机器 |
| BIOS/DOS 服务 | 本章没有提供者 | 没有安装，不参与执行 |

“AX 被写成 1234h”包含两个不同来源：CPU 固有的是 **如何执行 MOV**，程序外部提供的是 **本次要写入哪个值**。

初始 IP=0 也不是 CPU 永久写死的启动规则。真实 PC 有复位入口和固件启动路径；本章为了跳过尚未讲解的固件，显式由宿主准备实验状态。

网页上的“输出”是调试仪器在查看 CPU，不是这台机器已经接上显卡。

### 2.1 两台“机器”同时存在

使用浏览器实验时，实际上存在两个层次。真实电脑的 CPU 执行浏览器和 JavaScript 引擎，JavaScript 引擎再执行我们编写的 TypeScript 编译结果；而那段程序所维护的数组和数值，代表的是一台假想 8086 的状态。

这台假想机器叫客体，运行它的真实环境叫宿主。客体的 AX 是我们保存的一个 16 位值，不是直接把真实电脑的 RAX 暴露给网页。点击“单步”，也是宿主调用一次模拟函数，不是让真实处理器只执行一条自己的机器指令。

分清这两个层次，才能理解为什么我们能把客体停住、查看所有寄存器，甚至重置它：宿主仍然在运行，只是暂时不再推进客体状态。以后说“CPU 停机”时，也必须先说明是客体停机，还是宿主程序结束。

## 3. 必要准备：字节、位宽和地址

### 3.1 寄存器与内存不是两种变量名称

在高级语言里，我们常把各种存储都写成变量，看起来区别不大。对机器而言，寄存器和内存却有不同的访问方式。寄存器是 CPU 架构直接命名的一小组状态，指令可以指定 AX、BX；内存则是一系列按地址定位的字节，访问时要先确定地址，再读出或写入内容。

本章不需要展开真实处理器内部的存储电路，也不把寄存器简单等同于“更快的内存”。重要的是接口不同：MOV 的这个编码直接指定一个寄存器作为目的地，不需要再提供内存地址。后面讲数组时，才会学习如何从地址取数据。

IP 又有特殊职责。它不是这八个通用寄存器之一，而是告诉机器下一次应从哪里开始取指。在完整 8086 中，取指还要结合 CS；本章暂时省去分段，把 IP 直接当作这块平坦内存里的位置。这样做的边界必须记住，否则以后容易把“偏移”和“物理地址”混为一谈。

### 3.2 同一个数可以写成不同形式

一个字节有 8 位，取值是 0～255；两位十六进制数恰好表示一个字节。`B8` 是一个字节，不是两个字符。

网页文本框里的 `B8` 确实由两个字符组成，但装载前，宿主会把这两个字符解析成数值 184，存入一个字节的位置。CPU 核心读取的是这个数值，不是在识别字符 B 和 8。十六进制只是我们观察和书写二进制内容的一种方便形式。

十六进制一位对应四个二进制位，因此特别适合描述机器状态：B 对应 1011，8 对应 1000，合起来就是一个字节。无论你把它写成十进制 184、十六进制 B8，还是二进制 10111000，代表的位模式都一样。

AX 是 16 位寄存器，能保存 `0000h`～`FFFFh` 的位模式。AX=1234h 在十进制下是 4660。这个位模式本身不附带“整数类型”；怎样解释它取决于指令和软件约定。

“16 位”描述的是能保存多少个二进制位，不是十进制数有多少位。它一共有 65536 种可能的位模式。我们暂时按无符号数理解它们，下一章会看到同一组位也可以解释成有符号数，而 CPU 不需要在寄存器旁边再贴一个类型标签。

### 3.3 地址是位置，内容是位置里放的东西

内存按字节编址。三个字节顺序排列如下：

| 地址 | 字节 | 角色 |
|---|---|---|
| 0000 | B8 | 操作码：把立即数写入 AX |
| 0001 | 34 | 立即数低 8 位 |
| 0002 | 12 | 立即数高 8 位 |

这里的 0001 是地址，34 是内容，两者不能互换。IP=0001 意味着下一次读取内存中的第 1 号位置，不意味着要执行操作码 01；真正读到什么，取决于那个位置里装了什么。机器码页面把地址和字节排在一起时，最常见的初学误解之一，就是把左边的位置和右边的内容看成同一种数。

另一个容易混淆的词是“立即数”。它并不是“马上计算出的数”，而是直接跟在指令编码中的操作数。这次 MOV 所需的 1234h 就在后面两个字节里，CPU 不必再去另一个数据地址寻找它。

CPU 拼装立即数：

```ts
const value = low | (high << 8); // 34h | 1200h = 1234h
```

低字节在前称为小端字节序。不是浏览器把 3412h 自动换成 1234h，而是译码规则明确要求这样组合字节。

可以从权重来理解这行代码：低字节负责数值的低八位，高字节要乘以 256，才能放到高八位的位置。`high << 8` 完成这种位置移动，按位或 `|` 把互不重叠的两部分合起来。这里不是逻辑或 `||`；后者是在判断真假，不能用来拼接位。

小端也不是“把寄存器中的数字倒过来”。当我们写 AX=1234h 时，仍按照通常方式把高位写在左边。只有在把多字节数放进按地址排列的字节序列时，才需要规定哪个字节先出现。在这条指令里，这个顺序由 x86 编码规定；单独一个字节内部的二进制位并没有被反转。

寄存器数组使用机器编码规定的顺序：

```text
索引  0   1   2   3   4   5   6   7
寄存器 AX  CX  DX  BX  SP  BP  SI  DI
操作码 B8  B9  BA  BB  BC  BD  BE  BF
```

本章只是把 SP/BP/SI/DI 当作可写的 16 位寄存器，并没有因此实现栈或字符串指令。

把这组顺序作为数组顺序，是教学实现做出的直接选择。真实硬件并不必须用这样一个数组保存寄存器，完整工程也可以采取其他内部结构。双方必须保持的是“B8 写 AX、BB 写 BX”这样的架构关系，而不是变量的排列方式。

## 4. 先写出最简单的执行模型

在编写核心之前，先想一个问题：机器码中没有“这是第几行”的信息，CPU 如何知道程序应当继续执行哪条指令？

答案就在 IP 和指令长度的配合里。CPU 从当前 IP 取出操作码，译码规则决定还要读取多少个操作数字节；读完后，下一个位置就是顺序执行时下一条指令的起点。这里既不需要源码行号，也不需要在每条指令后放一个分隔符。指令边界是通过编码规则识别出来的。

从原理上看，执行循环只有三件事：

```text
内存中的字节 → 取指和译码 → 更新机器状态
                       ↑
                  下一次从新 IP 开始
```

先用伪代码表达：

```ts
while (!halted) {
  const opcode = memory[ip++];
  execute(opcode);
}
```

这段伪代码还没有描述立即数、截断输入和指令长度，不能直接声称它是一台完整的 8086。本章完整实现放在 [core.ts](../../teaching/ch03/src/core.ts)。

### 4.1 “取指”“译码”“执行”分别在说什么

取指是在内存中取得当前指令需要的字节；译码是在这些字节里认出操作和操作数；执行是按规则修改寄存器、内存或其他状态。三者联系紧密，但不应合并成一个模糊的“读代码”动作。

以 B8 34 12 为例，取指取得 B8；译码知道这是一个写入 AX 的 16 位立即数 MOV，并要求再读取两个字节；随后把 34 和 12 拼成 1234h，执行写入。最终，指令总共占用三个字节，下一条指令从 0003 开始。

在本章代码里，这些活动可能只相隔几行语句。真实处理器却会通过内部控制逻辑、寄存器和数据通路完成它们。我们不是在复刻每根导线，而是在实现软件能够观察到的行为。理解这个区别，既能避免把模拟器代码误当成芯片电路，也能避免觉得“不是画电路就没有学到原理”。

### 4.2 内存不会替 CPU 标注“这里是指令”

对于本章的内存数组，B8、34、12 都只是普通字节。我们在表格中标出“操作码”和“立即数”，是因为知道从 0000 开始的编码怎样解释，而不是内存为它们保存了永久的角色标签。

假如错误地从 0001 开始取指，CPU 会把 34 当作操作码，而不会自动跳回 0000 告诉你“这里是上一条指令的数据”。本章尚未支持 34 对应的指令，会报未实现；完整 CPU 则可能继续按它支持的编码解释。程序为什么会跑飞，很多时候就与这种边界错位有关。

这也解释了为什么入口位置是装载过程的一部分。只把字节放进内存还不够，还必须告诉机器从哪里开始。后面学习 EXE、引导和中断入口时，仍然要检查这个问题。

## 5. 机器状态与宿主装载

核心保存内存、寄存器、IP、FLAGS 和运行状态。内存为 `Uint8Array`，寄存器为 `Uint16Array`。

“机器状态”不是一个抽象口号。它指的是决定后续行为的那些保存下来的信息：同样的字节，如果 AX 原值不同、IP 不同或停机状态不同，执行结果就可能不同。模拟器把这些信息显式保存起来，才有可能单步、重置和对照。

我们选用定宽数组，是为了让存储宽度在代码里清楚可见，而不是宣称 JavaScript 的数值运算已经等同于 8086 运算。数组能够存储 16 位值；至于加法怎样截断、如何产生进位标志，仍须在下一章明确实现。

### 5.1 为什么每次实验要从已知状态开始

如果上一次执行留下了 AX=1234h，新实验碰巧也应该得到这个值，仅查看最终 AX 就可能误以为新程序已经执行过。统一的初始状态可以排除这类混淆，让变化的原因更容易确定。

真实系统中，启动状态和程序入口状态也有来源，但它们不是同一回事。CPU 复位建立的是体系规定的起始条件，固件随后运行，装载器再为程序安排环境。本章把其中的大部分步骤压缩成宿主装载，目的是隔离第一条指令，而不是否认那些层次的存在。

装载器执行：

1. 检查输入是非空的合法字节，长度不超过 64KB。
2. 清空实验内存，把程序复制到地址 0。
3. 清零寄存器，设置 IP=0、FLAGS=0002h。
4. 清除上次的停机或错误状态。

合法输入检查在任何修改之前完成。因此输入 `100` 这样的三位十六进制“字节”，或直接传入数值 256，不会半途覆盖旧机器。

这里记录已装载代码长度，防止缺失的立即数字节被剩余零内存默默补齐。**这是教学输入保护，不是真实 CPU 能识别“程序文件长度”。** 真 CPU 继续读取可访问内存，并不知道文件原来只包含两个字节。

这里其实有两个不同的检查。装载前检查每个输入是否为合法字节，保证送进机器的数据形式正确；执行时检查是否还有足够的已装载字节，保证我们没有把实验材料的缺失误读成一条完整指令。二者都帮助教学，但都不是 DOS 或 BIOS 在幕后修复程序。

判断模拟器的行为时，应分清这类额外保护和客体硬件异常。前者回答“实验输入是否完整”，后者回答“客体操作是否违反架构规则”。以后实现异常处理程序时，不能简单把这里的 JavaScript 错误当作已经完成了中断向量、压栈和返回机制。

FLAGS=0002h 是本章简化初值，MOV 和 HLT 都保持它不变；尚未完整建模各代 CPU 的 FLAGS 保留位。完整项目的 8088 会显示 F002h，两者不能因此判断为 MOV 行为不同。

## 6. 实现 MOV 与 HLT

### 6.1 从一条 MOV 推广到一组 MOV

如果为 AX、CX、DX 等分别写八段几乎相同的逻辑，很快就会发现真正变化的只有目的寄存器。本章使用的这组编码恰好把寄存器编号放在操作码的低三位中，所以可以先判断范围，再用减去 B8 得到索引。

例如 BB-B8=3，对应数组中的 BX。立即数依然占两个字节，拼接规则也不变。这样的一小段公共逻辑来自指令编码本身的规律，不是为了炫耀代码技巧；理解编码，通常能让实现反而更简单。

完整实现中的核心译码可以这样阅读：

```ts
if (opcode >= 0xb8 && opcode <= 0xbf) {
  const low = fetch8(), high = fetch8();
  registers[opcode - 0xb8] = low | (high << 8);
} else if (opcode === 0xf4) {
  status = 'halted';
} else {
  throw new Error('本章未实现这个操作码');
}
```

MOV 消费三个字节：一个操作码和两个立即数字节。HLT 只消费一个字节。

MOV 这个名字可以译作“传送”，但这里不是把源值拿走。执行之后，内存中的 34 和 12 仍然存在，只是 AX 获得了由它们表示的值。程序字节不是会随着执行被消耗掉的材料，“消费三个字节”说的是取指位置经过它们，不是把内存清空。

### 6.2 为什么使用局部游标

`step()` 使用局部取指游标：先读够本条指令，再执行修改，成功后才提交 IP。指令截断时，IP 保留在指令起点，目标寄存器不修改，并明确进入教学错误状态。

可以把局部游标理解成一次尝试中的读取位置。开始时它等于 IP，读 B8 后来到 1，读 34 后来到 2，读 12 后来到 3；只有这些读取足够支持完整执行时，我们才把最终位置保存回 IP。这样，缺少高字节时，面板上仍能指出出错指令从哪里开始。

这不意味着真实 CPU 的指令指针必须按同样的变量更新顺序工作。它是教学实现为了使错误状态清楚而选择的组织方式。对照时应检查成功指令结束后 IP 是否正确，以及本章声明的错误契约是否成立，不要求另一个核心也使用名为 cursor 的局部变量。

这只是当前支持的简单指令的错误契约，不代表真实 CPU 的所有异常都具有全事务回滚。以后讲复杂指令和缺页时，要重新讨论部分完成的行为。

IP 按 16 位回绕。对短程序，超过装载边界会报教学错误；完整 64KB 映像可以按 16 位游标回绕取指。

真实 HLT 等待符合条件的事件唤醒。本章没有中断源，因此 HLT 只进入稳定的停机状态。再次调用 `step()` 不推进 IP，也不修改寄存器。不要把它理解成 DOS 的程序退出服务。

### 6.3 停机、暂停和退出不是一回事

点击宿主的单步按钮，一次只推进一条指令，是观察者在控制模拟速度；执行 HLT，则是客体执行了一个改变自身状态的指令。这两种停止的来源不同。

程序退出又是另一层含义。操作系统通常还要处理程序资源、返回状态和后续调度；仅有 HLT 的核心不具备这些职责。因此本章用它作为明确的实验终点，而不是假装已经实现了进程结束。

HLT 执行后 IP 指向它后面的字节，也不表示已经继续执行了下一条指令。IP 可以保存继续执行的位置，停机状态则决定当前是否允许继续推进。两个状态一起描述机器行为，单看其中一个可能误判。

## 7. 实验一：先预测，再运行

打开 [第 3 章实验页](../../teaching/ch03/index.html)，选择“第一条指令：MOV 与 HLT”。

机器码：

```text
B8 34 12 BB CD AB F4
```

对应汇编：

```asm
mov ax, 1234h
mov bx, 0ABCDh
hlt
```

本页不带汇编器；汇编是便于人读的解释，真正被装载的是机器码文本框中的字节。

在按“单步”之前，写下预测：

| 时刻 | IP | AX | BX | FLAGS | 状态 |
|---|---|---|---|---|---|
| 装载后 | 0000 | 0000 | 0000 | 0002 | ready |
| 第 1 步后 | 0003 | 1234 | 0000 | 0002 | ready |
| 第 2 步后 | 0006 | 1234 | ABCD | 0002 | ready |
| 第 3 步后 | 0007 | 1234 | ABCD | 0002 | halted |

逐步执行后，观察内存中程序字节没有改变，而寄存器发生了变化。点击“检查断言”，验证实际经过的检查点，而不是仅检查最后一张画面。

第一次单步时，建议不要同时盯着所有数字，而是只追三件事：从哪个位置开始、用了哪些字节、改变了哪个寄存器。第一步从 0000 开始，使用 B8 34 12，写 AX，最后来到 0003；第二步从 0003 开始，使用 BB CD AB，写 BX，最后来到 0006。你应当能够把面板变化重新解释成这几句话。

如果 AX 正确但 IP 错了，机器仍然不正确，因为下一步会从错误位置取指。如果 IP 正确但 BX 被提前改动，也不正确，因为 MOV AX 的目的地只有 AX。检查中间状态就是为了避免“最后恰好得到期望数字”掩盖执行路径中的错误。

取消“安装观察模块”，重新装载并运行，再检查断言。结果应相同。这说明显示仪器不是执行这些指令所必需的组成部分。

这里不是说真实硬件的寄存器总能随便读出来，而是在区分运行接口和观察接口。实验工具有额外的查看能力，它应当不改变被查看的对象。以后遇到“读一次就清除状态”的设备寄存器时，这个区别会更重要。

## 8. 实验二：改变输入，不改变规则

选择“交换立即数的两个字节”，机器码是：

```text
B8 12 34 F4
```

应得到 AX=3412h。改变的是应用字节，CPU 的小端规则并没有改变。

这个实验的价值在于让你把“规则变了”和“输入变了”分开。如果每次想得到新值都要修改 CPU 核心，机器就没有形成可复用的指令机制；如果核心不变，只改变程序字节便能得到相应结果，那么编码规则确实在解释外部输入。

也可以修改文本框，随后点击“装载 / 重置”。所选实验的断言仍保持原预期：如果把第一项实验改成 AX=3412h，原来的 AX=1234h 检查应失败。不要为了让实验显得成功而自动修改预期。

## 9. 失败实验：不悄悄代替你补完机器

### 9.1 缺一个立即数字节

选择 `B8 34`。取指应明确报告“指令字节不足”，IP=0，AX=0。它不是客体的 #UD 或其他 CPU 异常，而是宿主教学契约的错误。

### 9.2 CPU 不自带 DOS

选择 `CD 21`。真实编码含义是 `INT 21h`，但本章既没有实现 INT，也没有安装 DOS，所以先报告未实现操作码 CD。

这里不能得出“INT 21h 就是 DOS”的结论。将来 CPU 负责进入当前向量指定的程序，DOS 才负责定义和安装文件/字符服务。向量可以被其他软件替换。

不妨把问题拆成两层：CPU 能否执行 INT？当前入口有没有一段提供所需服务的程序？本章第一层就还没有实现，因而不能通过这个失败实验直接观察第二层的缺失。将来补上 INT 后，即使编码能够执行，也仍然要检查入口的来源和内容。这样的分层问法，比一句“这个功能不支持”更有助于定位原因。

## 10. 固定不变量与自动测试

本章的测试在 [tests/core.test.ts](../../teaching/ch03/tests/core.test.ts)，实验与检查点在 [experiments.ts](../../teaching/ch03/src/experiments.ts)。

应持续成立：

- 内存字节和寄存器值处于声明的位宽范围。
- 观察返回副本，修改副本不改变核心。
- 输入装载失败不破坏旧状态。

操作完成后检查：

- MOV 的 IP 增加 3，只修改编码指定的寄存器，FLAGS 不变。
- HLT 消费一个字节，重复单步不再修改状态。
- 截断指令不提交半个 MOV。
- 重新装载能从错误状态恢复。

例如，第一条 MOV 的关键断言等价于：

```ts
expect(state.ip).toBe(3);
expect(state.registers[0]).toBe(0x1234);
expect(state.registers[3]).toBe(0);
expect(state.flags).toBe(2);
```

这些断言不要求工程 CPU 使用相同数组布局；跨实现对照时应映射到架构状态，并排除本章未建模的保留位差异。

不变量与操作结果也略有不同。“寄存器始终处在 16 位范围内”是持续约束；“第一条 MOV 后 AX=1234h”是某个具体输入对应的结果。前者帮助防止整个模型失去边界，后者帮助验证一条操作确实实现了声明的行为。两种检查结合起来，才不至于只知道机器“看起来还能跑”。

工程核心要同时满足很多程序的需求，而教学核心要使一个概念能够被单独看清。二者的不同不是正确与错误的区别，而是当前承诺范围和组织方式的区别。后续章节会逐步解释为什么那些额外逻辑需要存在。

## 12. 古今对照：第一条指令今天还在吗

以 x64 Windows 11/Linux 中的原生 64 位代码为例：

- MOV、寄存器、指令指针和机器码仍是核心概念；现在也有 RAX、RIP 等扩展。
- 指令字节仍由软件提供，CPU 固定实现的是编码和执行规则。
- 小端字节序仍存在。
- 同一个 B8 编码的完整含义与执行模式、前缀有关。不能把本章三字节译码直接用于原生 x64 代码。
- 普通应用不能随意执行 HLT；权限由 CPU 检查，操作系统管理特权状态。
- 现代 CPU 常用流水线、乱序执行等提高吞吐量；本章逐步解释的是对软件可见的执行结果，不是内部每一拍的电路。

参考：[Intel 架构手册入口](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)。阅读指令说明时注意适用模式与权限，不只查看助记符。

因此，学这一小段旧指令不是为了把现代电脑当作一台更快的 8086。它给我们建立的是一个长期有效的阅读方法：先找程序提供的编码，再确认执行模式和操作数宽度，最后检查状态变化。随着架构扩展，规则会增多，但不能跳过这几步，只凭一个助记符猜测机器做了什么。
