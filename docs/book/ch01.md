# 第 1 章：我们究竟要模拟什么

> 本章目标：画出一台计算机的职责地图，建立一个可以检查、可以修改、可以复现的内存状态模型。此时还没有 CPU，也不能执行程序。
>
> 配套工程：[ch01](../../teaching/ch01/README.md)。在完整项目启动开发服务器后，打开 `/teaching/ch01/index.html`。以下使用的是本章独立模型，不是完整虚拟 PC 在后台代跑。

## 1. 从“程序能跑”到“知道是谁让它跑”

我们可能已经会写程序，知道 CPU 执行指令，知道内存保存数据，也知道操作系统管理硬件。但是，把这些句子连起来，仍然不一定能回答一个很具体的问题：程序输出字母 `A` 时，究竟发生了什么？

一种常见回答是“调用输出函数，然后显示在屏幕上”。这对于使用接口已经足够，对于理解机器却不够。输出函数是谁写的？CPU 有没有一条“显示字母 A”的指令？字母的点阵在哪里？谁决定它出现在第几行？如果没有操作系统，这个字母还能显示吗？

这些问题的困难不在于某一个知识点特别深，而在于我们通常同时使用了多个层次，却没有把它们拆开。高级语言、库、操作系统、固件、CPU、设备都参与了工作。一个层次提供机制，另一个层次填入参数，还有一个层次规定使用方式。只看最后的效果，很容易把它们统称为“计算机做的”。

本书想采取相反的路线：先造一台能力非常少的机器，少到我们可以解释每一次状态变化；然后逐步加入新能力。每加一层，不仅问“怎么实现”，还要问“谁提供了什么”。直到能够运行较复杂的软件，仍然可以把一个现象沿着调用关系和数据流追溯到源头。

这也是为什么本书不会从“写一个可以运行 Windows 的模拟器”开始。这样的目标太大，容易把尚未理解的能力藏在框架、库或现成代码里。我们的第一件成果甚至不执行指令：它只是一块内存。这个起点看起来不起眼，但它能够迫使我们先说清楚，什么是机器状态，什么是外部操作，以及什么仍然不存在。

## 2. 一台机器不是一个大函数

### 2.1 最小职责地图

先把未来要搭建的计算机画出来。这里的箭头表示信息传递和访问关系，不表示本章已经实现了这些部件。

```text
              程序、初始数据、输入事件
                        |
                        v
                 固件 / 操作系统 / 应用
                  （都包含可执行代码）
                        |
                        v
                  CPU <----> 内存
                   |
             总线 / 端口 / 地址映射
                   |
         显示、键盘、定时器、磁盘控制器

宿主：装载、运行调度、浏览器界面、观察和测试
      位于被模拟机器之外，不等于客体操作系统
```

CPU 是状态变化的执行者之一。它有寄存器、当前指令位置、标志位等状态，并根据指令编码执行既定规则。内存则提供按地址保存和取回字节的能力。设备通过约定好的接口响应读写，可能还会在将来的某个时刻产生事件。

注意，固件、操作系统和应用程序不应该画成 CPU 内部天然存在的三个功能开关。它们主要是代码和数据，必须以某种方式进入机器。CPU 执行它们的指令，与执行我们自己写的指令，使用的是同一套基本机制。它们的身份来自装载过程、运行位置、权限和软件约定，而不是某个字节天生带有“这是操作系统”的标签。

这张图还省略了缓存、总线仲裁、实际电路时序等很多东西。省略不是说它们不重要，而是当前的问题还不需要它们。模拟工作的第一项选择，就是规定希望解释的现象。若目标是理解一条指令为什么改变寄存器，功能性状态模型可以先于晶体管、电压和时钟波形；若目标是解释总线竞争造成的精确延迟，仅有这样的模型就不够。

### 2.2 机制、参数和策略不要混为一谈

假设未来的 CPU 遇到一条加法指令。如何识别这条指令，如何取操作数，结果保留多少位，哪些标志需要更新，这些属于 CPU 的既定机制。我们不能通过在内存里放一段普通程序，随意重新定义某个已有指令编码的硬件语义。

但是，加哪两个数、把结果用来做什么，由程序选择。程序可能是应用，也可能是操作系统或固件。结果放进寄存器以后，要不要写到屏幕、写到磁盘或者作为循环次数，又是后续代码作出的决定。

真实 CPU 的机制由电路以及某些处理器中的微码共同实现，不能把所有指令都想象成“一条指令对应一段操作系统函数”。在我们的虚拟机里，这些机制由 TypeScript 实现。实现语言变了，职责没有变：模拟器中的加法处理函数是在扮演 CPU，不是在扮演客体应用。

“由 TypeScript 写成”也不意味着所有 TypeScript 都属于虚拟 CPU。按钮处理函数、浏览器页面渲染、源码下载同样使用 TypeScript，却属于宿主工具。判断归属要看它在模型中扮演什么角色，而不是看它使用什么语言。

本书以后解释一个功能时，会反复使用以下问题：

1. 哪些规则是 CPU 或设备固定提供的？
2. 哪些数值、地址和事件来自外部输入？
3. 哪些代码由固件、操作系统、驱动或应用提供？
4. 哪些动作仅由模拟器宿主提供，真实客体不能这样做？

最后一个问题尤其重要。浏览器中的“修改内存”按钮可以绕过将来 CPU 的取指、权限检查和指令执行流程。这是调试便利，不是给客体程序增加了一条万能写内存指令。

## 3. 程序从哪里来，机器如何“知道下一步”

### 3.1 内存里的代码仍然是字节

在我们习惯的编程环境里，程序看起来是一个有名字的文件。点一下运行按钮，它就开始执行，似乎机器天然认识“这是程序文件”。

但在 CPU 能执行之前，源代码通常还要经过编译或汇编，形成机器码；文件中的内容还要由装载过程放进内存；CPU 的入口状态还要被设置好。高级环境把这些步骤包装起来了，它们并没有消失。

对于本书将要实现的普通内存，一串机器码和一串数据在存储形式上没有区别：都是字节。字节 `B8` 放在内存里，并不会自己开始执行。它是否被当作指令，要看 CPU 是否把当前位置指向它，并按当前模式的指令规则读取它。

同样的道理，文件中的字符 `A` 可以作为文本、数字 65、指令中的立即数，或者某个二进制结构的一部分。内存负责保管位模式，不负责替软件决定意义。第二章会把这个问题讲得更细。

### 3.2 初始状态也是来源明确的输入

如果一台机器刚被造出来，内存里有什么，CPU 从哪里开始，设备处于什么状态？这些都不是可以含糊带过的问题。

真机存在处理器规定的复位状态和平台规定的启动安排。处理器从规定的入口开始取指，而平台必须让这个地址对应到适当的固件内容。随后固件初始化硬件，选择启动路径，装入下一阶段软件。这里已经有多个提供者：处理器定义入口规则，平台安排地址映射，固件提供入口处的代码。

本书早期实验不会立即模拟完整启动。宿主会直接准备程序和入口状态，以便把注意力集中在取指和执行上。我们应明确说“宿主直接装入”，不能把它描述成“BIOS 已经启动了程序”。

本章更简单：构造内存对象时，所有字节初始化为零；按下“重置实验”时，再次清零。这是为了实验可复现而选择的模型规则，不是关于所有真实 RAM 上电内容的断言。断电后的 RAM 不会因为“默认数组是零”就自动遵循 JavaScript 的初始化行为。

### 3.3 固件不是指令语义的来源

“BIOS 提供基本输入输出”这个名字，很容易让人误以为所有基本能力都来自 BIOS。其实 BIOS 使用 CPU 和设备已经提供的能力，编写出更方便的服务接口。

在后续章节中，我们会看到显示服务、读盘服务以及中断入口。CPU 负责某种中断机制，例如找到入口、保存必要现场并转移控制；入口处做什么，取决于那里实际放了谁的代码。中断服务程序可能由 BIOS 安装，可能由操作系统安装，也可能由应用替换或串接。

因此，仅知道“调用了某个中断号”还不够。要追问当前入口指向哪里、谁设置了它、处理程序内部又调用了什么。这里先建立问题意识，不提前实现中断；到相关章节，我们再用真实轨迹把这个判断落实到代码和状态。

## 4. 虚拟机、宿主和观察窗口

### 4.1 浏览器不是客体的世界

本书的虚拟机运行在浏览器中。浏览器属于宿主运行环境；我们模拟的 8086–80486 机器属于客体模型。未来客体里的 DOS，不是浏览器所运行的操作系统；未来客体的内存，也不是让客体程序任意操作浏览器内存的通道。

我们会用 `Uint8Array` 保存客体字节。这块数组是宿主程序分配的，但是在约定的接口之内，它代表客体 RAM。两者的联系由模拟器建立：客体地址 16 对应数组中的一个位置，并不意味着真实宿主物理地址也是 16。

类似地，客体屏幕可能最后被浏览器绘制在一个画布上。画布是宿主表示结果的方式，不是客体内部额外存在的一块神奇显示设备。必须先定义客体如何输出，再由宿主把结果呈现出来。否则，很容易在“写一个好看的演示界面”时，跳过本来要解释的硬件过程。

### 4.2 功能模拟不等于逐晶体管复制

我们要实现的是一个逐步增长的功能模型：给定状态和输入，按照规定规则产生下一状态和输出。它可以模拟寄存器、内存和设备行为，而不必一开始模拟每一根导线。

这也意味着早期代码与完整项目的优化代码可以不同。第一版可以直接读数组，后续版本可能加入地址转换、快路径和缓存。比较两者时，应先明确它们承诺哪些行为相同，再针对这些行为检查，而不是要求代码长得一样。

功能模型也有适用边界。没有定义周期和设备时序时，运行得快或慢不能证明真实硬件会这样耗时。以后加入虚拟时间，也必须区分客体时间与浏览器刷新时间。页面暂停几秒，并不应悄悄改变一台按确定输入运行的客体的逻辑结果。

### 4.3 为什么观察工具要放在核心之外

观察工具应该帮助我们回答“内存里现在有什么”，而不成为答案产生的必要条件。如果关闭观察窗口，机器就不能继续运行，那么我们很可能把模型和界面耦合在了一起。

本章的核心不导入 DOM，不知道按钮和文本框，不负责格式化输出。它只有内存及少数操作。宿主把模型接口接到页面上；观察模块只读取值和副本。卸载观察模块之后，实验仍使用同一套核心和断言。

这里所谓“插件”先采用最小形式：一个可安装、可卸载的观察模块，不是带动态发现、权限系统和版本协议的大型插件平台。先守住读取边界，远比一开始设计许多扩展接口更重要。

## 5. 本章真正搭起来的东西：一块内存

### 5.1 为什么选 64KB

我们先使用 65,536 个字节，地址从 0 到 65,535，也可以写成 `0000h` 到 `FFFFh`。这个规模与后续 16 位偏移的讨论容易衔接，又足够小，方便完整检查状态。

但这不是“8086 只能访问 64KB”的结论。8086 使用分段地址，可以形成 20 位物理地址，通常描述为 1MB 地址空间；一个 16 位偏移有 64KB 取值范围。分段和物理地址计算要到第 6 章才进入教学模型。

所以当前地址只是这块教学内存的下标。我们没有实现段寄存器、地址总线宽度或地址回绕机制。接口规定越界报错，这是一条教学 API 的边界，不是提前宣布了真实 x86 越界会产生哪种异常。

### 5.2 最小接口

[核心代码](../../teaching/ch01/src/core.ts)提供以下操作：

```ts
const memory = new Memory();
memory.write8(16, 65);
const value = memory.read8(16); // 65
const copy = memory.peek(16, 1);
memory.reset();
```

`read8` 和 `write8` 中的 `8` 指八个位，也就是一个字节。地址选择位置，数值指定写入的内容。把这两个参数分别看清楚，比记住函数名字更重要。

如果在地址 16 写入 65，并不意味着内存建立了“16 与 65 相互关联”的关系。地址 65 的内容不会因此改变。这只是一个位置保存了一个值，附近位置也不会自动受影响。

`reset` 清零整块内存。`peek` 返回指定范围的副本。后者是观察边界的一部分：调用者可以修改副本，但是修改副本不能反过来改变客体内存。

```ts
memory.write8(16, 65);
const snapshot = memory.peek(16, 1);
snapshot[0] = 0;
console.assert(memory.read8(16) === 65);
```

如果这里返回原数组的视图，调用者就能绕过 `write8` 的检查修改核心状态。那时“观察接口”实际上已经成为第二条写入路径。使用副本，是用少量宿主开销换取清晰的职责边界；本书早期优先选择后者。

### 5.3 输入错误为什么要明确拒绝

`Uint8Array` 可以自动把一些输入转换为八位数。例如，写入 256 可能得到 0。这个行为对某些算法很便利，却不能成为本章接口的隐含规则。

我们希望区分两件事：

- 调用者声称写一个字节，却提供了超范围值：这是实验输入错误。
- 已定义的机器运算产生超出位宽的数学结果，并按规则保留低位：这是将来 ALU 的行为。

如果都交给数组自动转换，读者就分不清零来自错误输入被吞掉，还是来自已经实现的运算规则。因此，`write8` 先检查地址和数值，再写入：

```ts
write8(address: number, value: number): void {
  this.checkAddress(address);
  if (!Number.isInteger(value) || value < 0 || value > 0xff) {
    throw new Error('字节必须位于 0～255');
  }
  this.bytes[address] = value;
}
```

检查通过才允许改变状态。失败时原内存保持不变。这个顺序不仅是为了提示友好，更是一个可检验的状态不变量。

这里的 `Error` 是宿主 API 报告错误，不是 CPU 已经产生了异常。此时连 CPU 都没有，自然不存在异常向量、压栈现场或异常处理程序。以后我们实现客体异常时，会另外定义它的体系结构行为。

## 6. 贯穿案例的起点：保存一个字符，不是显示一个字符

我们选 `A` 作为贯穿案例。在 ASCII 编码中，它对应十进制 65，也就是十六进制 `41h`。这个对应关系来自字符编码约定，不来自内存硬件。

本章可以在内存中保存 `41h`，观察窗口可以把它显示成十进制或十六进制。若宿主把它转换成 `A`，那也是宿主使用编码约定解释了这个值。客体还没有显示设备，不能据此说它已经“输出了字符”。

后续章节会逐渐增加不同路径：

1. CPU 执行指令，得到或移动数值。
2. 程序把字符码和属性写入文字显存，显示设备按约定解释它们。
3. 固件封装显示设备操作，提供 BIOS 服务。
4. DOS 或现代操作系统提供自己的软件接口。

这些路径可能产生相似的可见结果，职责分工却不同。我们会保持字符这个例子不变，观察实现它的层次如何增长。

读取一个扇区和响应一次按键也是辅助案例。它们会分别揭示存储和输入路径。但现在不需要把磁盘、键盘的全部知识塞进第一章。先记住：一个数值进入内存以后，我们仍然要追问它是从哪里来的。

## 7. 实验：看见状态，但不伪装成执行指令

实验页面中的按钮叫“下一项宿主操作”和“完成本组操作”，而不是“执行一条指令”。记录区也明确写着“宿主操作记录”。名称不是修辞细节，它直接决定读者怎样理解刚才发生的事情。

页面上的操作由[实验定义](../../teaching/ch01/src/experiments.ts)提供，内存行为由核心提供，按钮和验收由[宿主](../../teaching/shared/memory-host.ts)提供，数值呈现由[观察模块](../../teaching/shared/memory-observer.ts)提供。没有 BIOS、操作系统或应用程序参与客体执行。

### 实验一：字节没有自动执行的能力

选择“状态有了，CPU 还没有”。先预测，把 `B8 34 12` 写入地址 0、1、2 后，接下来会不会发生什么。

第三章会说明这三个字节在特定上下文中可以编码一条指令。本章没有取指机制，所以它们只会留在那里。每按一次按钮，仅发生实验列表规定的宿主操作。

| 步骤 | 输入或操作 | 应检查的结果 |
|---|---|---|
| 1 | 读取地址 0 | 初始值为 0 |
| 2～4 | 分别写入 B8、34、12 | 每次写入后能够读回同值 |
| 5 | 查看地址 0 起的四个字节 | B8 34 12 00 |

本实验的不变量不是“程序执行成功”，而是“只有指定字节被修改，随后读取符合写入结果”。CPU 寄存器没有变，因为模型根本没有寄存器。

### 实验二：分清地址、内容和观察副本

选择“地址与内容是不同的数”。在地址 16 放入 65，随后读取地址 16 和地址 65。

预期前者为 65，后者仍为 0。实验还会取得地址 16 的观察副本，修改副本，再次检查原内存仍然保存 65。

这里有两条独立结论：地址与内容是不同角色；观察副本与机器状态也是不同对象。不要因为它们在页面中都表现为数字或数组，就把这些角色混在一起。

### 实验三：故意提供错误输入

选择“失败实验：不悄悄截断错误输入”。先在地址 0 写入 `41h`，然后尝试写入 256，再尝试访问地址 65,536。

实验将预期错误当作被检查的现象，但不忽略它：记录区应展示错误消息，并确认整块内存未发生变化。最后地址 0 仍是 `41h`。

通过本实验的标准不是“没有报错”，而是“在指定位置报了指定错误，且没有提交写入”。程序正确性有时正是正确拒绝一个操作。

### 再做两次手工观察

先完成任意实验并检查断言，然后取消“安装观察模块”，重置并再次完成。断言应仍然通过。重新安装观察模块，只会重新显示当前状态，不会重建或执行一台新机器。

再试着手工写入一个字节。页面应说明原实验验收需要重置，不能把原实验已经通过的检查当作修改后仍正确的证据。我们的观察工具允许宿主实验输入，但输入发生变化后，原先那套预期也必须重新考虑。

## 9. 与完整项目对照：先找边界，不急着读所有实现

完整 AsmPerfect 86 已经支持远超过本章的功能。[CPU 核心](../../src/cpu/cpu.ts)包含指令处理和机器状态；[整机组织](../../src/machine/machine.ts)负责把 CPU、服务和设备组合起来；[固件与 DOS 服务](../../src/machine/bios.ts)提供对应实现；[界面入口](../../src/ui/main.ts)负责宿主交互。

这些是实现职责的入口，不意味着一个文件只包含一个概念，也不意味着完整项目每个行为都逐条执行了真实 BIOS 指令。项目中部分 BIOS/DOS 服务采用高层陷阱模拟：客体执行到约定桩代码时，转入宿主实现的处理逻辑。后续章节必须把这种工程便利与真实固件执行过程分开。

现在阅读完整项目，只需要问三个问题：谁持有状态，谁改变状态，谁显示状态。不要试图第一天就看懂每一种指令优化。随着教学机器增长，再到完整实现里寻找相同机制，理解“为了支持更多行为，工程代码增加了什么”。

第一、二章不提供“在完整 CPU 中单步执行同一程序”的入口，因为目前没有客体程序可执行。启动页链接到独立状态实验；第三、四章开始提供关闭可选服务的同题 CPU 对照。让入口诚实地反映阶段，比强行统一按钮更重要。

## 10. 这些观念在今天还成立吗

在 x64 Windows 11 或 Linux 上，CPU、内存、设备、固件、操作系统和应用的职责区分仍然成立。很多具体接口改变了，但一个系统调用并没有因此变成 CPU 自动完成全部业务的单条指令。

现代处理器仍按指令规则工作，内存仍承载位模式，设备仍有接口。现代系统的地址转换、缓存、乱序执行、多个核心等机制更复杂，却没有取消“状态、输入、规则和输出”这个分析框架。

传统 PC BIOS 的某些服务已主要属于旧环境或兼容路径，现代 PC 常用 UEFI 固件建立启动环境。操作系统接管以后，普通应用通常通过库和系统调用请求输出或读文件，不使用 DOS 的 `INT 21h`。UEFI 也不是把所有运行期操作系统接口统一替代了；启动服务与操作系统正常运行后的服务仍然要分开。

本章的 64KB 数组则只是教学阶段选择，并不是现代内存容量或地址空间的缩小版标准。现代应用通常面对由操作系统建立的虚拟地址空间。它们看到的地址与物理 RAM、宿主数组下标之间，可能隔着多个映射层。

功能模拟仍是有用方法，但本项目不是只把一段客体代码直接交给宿主 CPU 执行的硬件辅助虚拟化方案。两者都可以提供“另一台机器”的运行环境，落实指令行为的手段不同。本书当前采用解释式功能模型，从明确的小规则开始学习。

## 11. 验收与思考

独立源码包在解压后包含 `ch01` 与相邻的 `shared`。进入 `ch01`：


构建产物可以由静态服务器提供给浏览器。不要把双击 HTML、使用 `file:` 打开模块脚本，等同于已经验证浏览器构建可运行。

自动测试覆盖操作序列、相邻字节不变、观察副本隔离、末尾字节重置，以及负数、小数和越界输入拒绝。实验页面检查实际读写和指定错误，不是仅比较屏幕文案。

请试着不用“计算机自动处理”回答这些问题：

1. 地址 16 中出现了 `41h`，本章中是谁写进去的？谁把它显示为十六进制？
2. 在地址 0 写入 `B8`，为什么没有发生指令执行？缺少哪种状态和机制？
3. 清零内存是本章哪一层提供的规则？能否把它直接推断为真实 RAM 上电规则？
4. 观察窗口关闭以后，哪些能力应保留？哪些信息只是暂时不可见？
5. 某个中断被调用时，为什么还要检查当前处理程序的来源？

本章最重要的成果不是 64KB 容量，而是一种工作方法：每次看到现象，都把状态、规则、输入和提供者拆开。下一章，我们保留这块内存，研究里面的位模式怎样被解释为数字；第三章再让 CPU 真正从这些字节中取出第一条指令。
