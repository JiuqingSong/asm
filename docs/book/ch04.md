# 第 4 章：ALU 与标志位

> 试验稿 pilot-1。本章继承第 3 章的机器状态、MOV、HLT 和装载规则，增加 ALU。独立源码为 `teaching/ch04`，运行不需要第 3 章目录或完整项目。

## 1. 从“搬一个值”到“算一个值”

上一章把程序提供的立即数放进寄存器。现在执行：

```asm
mov ax, 0FFFFh
add ax, 1
hlt
```

如果只看 AX，结果是零。但 FFFFh+1 在普通数学里不是零，机器有没有算错？

没有。16 位目的寄存器只能保留低 16 位，额外的信息由标志位表示。本章要区分三个东西：

> 完整数学结果、写入寄存器的位模式、对结果的有符号/无符号解释。

这一章的难点通常不是“加法怎样写”，而是我们带着日常数学或高级语言的直觉来理解机器。日常数学可以继续写出更大的结果，高级语言又常替我们处理数值类型；寄存器却只有固定数量的位，CPU 必须明确规定装不下时怎么办，以及如何把额外信息留给后续程序。

所以，请先把“溢出就是程序错误”这个印象放到一边。有些软件确实要拒绝越界结果，有些软件却正好利用定宽运算的回绕，例如分开处理一个大整数的多个部分。CPU 提供一致的机制，软件再根据用途制定策略。我们这次实现的不是“替用户判断数学是否有意义”的工具，而是一个能准确计算位模式并留下条件信息的 ALU。

如果读完后，你能解释“为什么 FFFFh+1 有进位却没有有符号溢出”，并能沿着代码找到这两个标志各自的来源，就已经抓住了本章最重要的联系。

## 2. 本章机器的能力边界

继承 64KB 平坦内存、8 个 16 位寄存器、MOV r16/立即数、HLT、16 位 IP、宿主装载和无副作用查看。

新增的都是 **AX 与 16 位立即数** 的专用编码：

| 操作码 | 助记符 | 写回 AX | 更新标志 |
|---|---|---|---|
| 05 | ADD AX, imm16 | 是 | CF/PF/AF/ZF/SF/OF |
| 2D | SUB AX, imm16 | 是 | CF/PF/AF/ZF/SF/OF |
| 3D | CMP AX, imm16 | 否 | 同 SUB |
| 25 | AND AX, imm16 | 是 | PF/ZF/SF，清 CF/OF；AF 未定义 |
| 0D | OR AX, imm16 | 是 | 同 AND |
| 35 | XOR AX, imm16 | 是 | 同 AND |

尚未支持：ADC/SBB、INC/DEC、8 位运算、其他寄存器或内存操作数、ModR/M、分支、栈、中断、设备和时间模型。

本章选用专用编码，以便先理解运算，不让寻址译码抢走注意力。不是说真实 ADD 只能使用 AX。

### 2.1 ALU 在整台机器中处于什么位置

ALU 是算术逻辑单元的简称。可以先把它看作数据通路中的一个部件：它得到操作数和操作选择，产生结果及相关条件信息。它不负责在内存中寻找整个程序，不负责判断现在应该执行第几条指令，也不负责把数字显示成十进制字符串。

上一章的取指与译码逻辑负责识别“现在是 ADD”，并从指令中取出立即数；寄存器提供另一个输入；运算逻辑计算结果；CPU 的控制逻辑再决定是否写回 AX。这些职责在教学代码里都属于一个类，但概念上仍然可以区分。将来改变操作数的寻址方式，不应该迫使我们重新发明加法规则。

本章把 ALU 的逻辑实现为普通函数调用。真实处理器通过电路完成这些活动，时钟和内部控制决定状态何时更新。我们用函数表达的是输入与结果之间的规则，不是在断言芯片内部真的运行着 TypeScript 函数。

### 2.2 为什么先把寻址范围限制住

一条指令的难度可能来自两个方向：如何找到操作数，以及找到以后如何运算。本章只处理后者。AX 的位置已经确定，立即数紧跟操作码，两项输入的来源都很清楚。这样，若结果或标志不对，就可以先集中检查 ALU，而不必同时怀疑段地址、内存读写和 ModR/M 译码。

范围有限并不等于可以随意改变规则。虽然只实现少量编码，但已经实现的 ADD、SUB 和 CMP 必须遵守它们对应的位宽与标志规则。以后扩大操作数范围时，才有可靠的基础可以复用。

## 3. 职责地图：类型和策略不在加法器里

在高级语言中，变量声明可能写着有符号或无符号类型，编译器根据类型选择后续操作。而在普通 16 位 ADD 面前，输入首先只是两个 16 位位模式。加法并不先询问“AX 是不是一个负数”，再选择另一套加法；同一次位运算就能同时产生无符号和有符号解释所需的信息。

| 内容 | 来源 |
|---|---|
| 操作码、位宽、结果截断、标志更新规则 | CPU 架构规定，核心模拟 |
| 本次加哪个数、执行哪些操作 | 应用程序的字节 |
| 数值按有符号还是无符号理解 | 指令语义与软件约定；普通 ADD 不需要一个“类型字段” |
| 如何根据 CF/OF 作决策 | 后续程序；条件跳转在下一章实现 |
| 初始寄存器和 FLAGS | 宿主装载，本章没有 OS 或 BIOS |
| 显示 AX、解释标志、检查断言 | 宿主观察与实验工具，不是 ALU 自带文本解释 |

ALU 产生 CF 和 OF，不会替程序弹出“算错了”的消息。`FFFFh` 本身既可以表示无符号 65535，也可以表示有符号 -1。

CPU 的标志位帮软件判断结果；使用哪个标志取决于软件要解决的问题。

例如，把 AX 看作计数器时，软件可能关心无符号数是否超出上限；把它看作带正负号的温度差时，软件可能关心有符号结果是否越界。CPU 可以为同一条 ADD 同时提供 CF 与 OF，但究竟使用哪个条件，来自程序的语义，而不是寄存器旁边的隐含类型。

也要把高级语言的数值规则与指令规则分开。某种语言或某个表达式允许怎样的溢出，是编译器和语言规范层面的事；我们这里实现的是已选定的机器指令执行后应该留下什么状态。不能因为宿主 JavaScript 的加法能容纳更大数值，就让客体 AX 也变成任意宽度。

## 4. 先看结果，再看解释

### 4.1 定宽数可以从“走完一圈”来理解

先不考虑正负号，16 位无符号位模式从 0 排到 65535。一旦只保存低 16 位，增加 65536 就会回到同一个位模式。可以把它想成有 65536 个刻度的计数器：走到最后一格后再前进一步，显示回到零。

这种解释对应模 65536 的运算。它不表示数学结果不存在，而是表示寄存器只保存结果在这一圈中的位置。加法的 CF 则告诉我们，这一次相加是否越过了这一圈的上界。结果与进位一起，比单独一个结果包含更多信息。

```text
FFFFh + 0001h = 10000h
保留低 16 位：0000h
```

有符号解释则是：

```text
-1 + 1 = 0
```

所以这个运算应当 CF=1、OF=0。无符号结果超出了 16 位范围，有符号结果却完全合法。

### 4.2 补码不是另外一种加法器

16 位补码把最高位权重解释为 -32768，其余位仍具有正的权重。因此 7FFFh 表示 32767，8000h 表示 -32768，FFFFh 则表示 -1。这些并不是三组不同的存储材料，而是对同样 16 位的另一种数值解释。

补码的好处之一是，位模式的加减结果可以与有符号整数运算衔接，而不必为负数单独准备一套“先处理负号、再算绝对值”的流程。只是在超过有符号可表示范围时，软件需要知道当前位模式已经不能代表原来的数学结果，这正是 OF 要表达的情况。

对 FFFFh+1 而言，无符号解释从 65535 越过上界，有符号解释却只是 -1+1。一个解释越界，另一个没有越界，因此 CF 和 OF 完全可以不同。它们不是两份重复报告，而是在回答不同的问题。

再看：

```text
7FFFh + 0001h = 8000h
无符号：32767 + 1 = 32768，可以表示
有符号：32767 + 1 超出 -32768～32767 的范围
```

所以 CF=0、OF=1。两个正数相加后出现负数位模式，是有符号溢出的信号。

### 4.3 符号位变了，不一定发生溢出

负数加正数时，结果跨过零而改变符号是很正常的。例如 -1+2 得到 1，符号从负变正，却没有超出有符号范围。仅仅观察结果最高位是否变化，不能判定 OF。

对于加法，两个异号输入不会使结果越过有符号范围的两端；风险出现在两个同号输入相加，结果却落入另一种符号的位模式。减法的条件不同，因为减去一个正数与减去一个负数对数值方向的影响不同。本章稍后会把这两个判断分别落实到公式，而不是混用一个“符号不一致”的直觉。

可以用下面几个例子校准理解。无需先运行代码，只按两种解释推导：

| 运算 | 保存的结果 | CF | OF | 关键原因 |
|---|---|---|---|---|
| FFFFh + 1 | 0000h | 1 | 0 | 无符号越界；有符号 -1+1 合法 |
| 7FFFh + 1 | 8000h | 0 | 1 | 无符号合法；有符号正数超过上界 |
| 8000h + 8000h | 0000h | 1 | 1 | 两种解释都越界 |
| FFFFh + 2 | 0001h | 1 | 0 | 有符号 -1+2 正常跨过零 |

这个表也说明，不能把 CF=1 直接读成“结果是负数”，不能把 SF=1 直接读成“发生了溢出”。每个标志都有自己严格限定的问题。

## 5. 把算术写得直接一点

### 5.1 先有可解释的完整结果，再明确截断

完整实现见 [core.ts](../../teaching/ch04/src/core.ts)。先看基本结果：

```ts
const full = subtract ? left - right : left + right;
const result = full & 0xffff;
const carry = subtract ? left < right : full > 0xffff;
```

这里 JavaScript Number 足够精确地表示两个 16 位整数的加减；我们显式截成 16 位，而不是借助宿主溢出。

两项输入的最大值都是 65535，相加最多为 131070，远在 JavaScript 能精确表示整数的范围内。因此，本章可以先算出 full，再通过 `& 0xffff` 保留低 16 位。我们没有因为宿主恰好用了某种数值类型，就省略客体的位宽规则。

对于非负结果，掩掉高位很直观。对于减法得到的负结果，JavaScript 的按位操作先使用 32 位整数位模式，最后的掩码取出低 16 位，得到我们需要的回绕结果。这里之所以适用，是因为本章输入范围和运算种类都受到限制；以后涉及 32 位乘法、64 位结果或浮点数时，要重新选择可靠的数值实现，不能无限推广这个写法。

同样不能只把结果写进 `Uint16Array`，就认为已经完成了运算。定宽存储可以留下低位，却不会替我们产生 CF、OF 和其他客体标志。如果在截断之后才试图恢复所有信息，就容易把已经丢掉的进位漏掉。

### 5.2 借位与负数结果有关，但不是同一个概念

减法中的 CF 表示借位。例如 0-1，数学结果为 -1，保留低 16 位得到 FFFFh，CF=1。CPU 不会因为无符号借位自动调用 BIOS。

对两个无符号输入而言，只要 left 小于 right，减法就需要借位。这就是代码直接比较 `left < right` 的原因。减法的 CF 含义由 x86 规定，不能想当然地把它等同于内部某种补码加法器的进位输出。

有符号解释则必须另看范围。例如 8000h-1 按无符号解释是 32768-1，不需要借位；按有符号解释却是 -32768-1，低于可表示下界。因此它的 CF=0、OF=1。加法与减法都有这种“双重解释”，不是只有正数相加才需要区分。

### 5.3 把溢出条件逐项翻译成位运算

有符号溢出的判定：

```ts
const overflow = subtract
  ? ((left ^ right) & (left ^ result) & 0x8000) !== 0
  : ((~(left ^ right)) & (left ^ result) & 0x8000) !== 0;
```

逐项解释：

- `0x8000` 选出 16 位符号位。
- 加法：两个输入同号，而结果符号与输入不同，才会溢出。
- 减法：两个输入异号，而结果符号与被减数不同，才会溢出。

不必第一遍就记住位运算公式。先用正负数分类验证它，再把公式当作实现。

具体看加法公式，`left ^ right` 在符号位上为零，表示两个输入同号；取反后，该位置变成一。`left ^ result` 在符号位上为一，表示结果与输入异号。两部分按位与，再只保留 8000h，便是在同时检查“输入同号”和“结果异号”。

减法不需要把第一部分取反，因为它要检查输入异号。这样，公式不是凭空出现的技巧，而是把前面用语言说明的条件变成一组布尔判断。你可以只关注被 8000h 选出的那一位，不必把每一个中间数的全部 32 位都算出来。

此处的按位非 `~` 在宿主中作用于 32 位数，并不直接表示“只翻转 16 位”。不过最后只检查符号位 8000h，所以额外高位不会参与判定。明确这个限制，比记住“按位非就是求补码”更准确；求补码、翻转位和改变数值解释也不是同一个动作。

## 6. 六个标志分别观察什么

FLAGS 可以先理解成一组保存条件信息的位，而不是一个普通运算结果。CPU 将这些位打包在同一个寄存器中，是为了让后续指令有明确的位置可读；每一位并不表示同一种条件。

它也不是日志。新的运算会根据指令规则覆盖相关位，不会自动保留“上一次加法发生过进位”的历史。因此，在查看 FLAGS 时，必须同时问：这些位最近由哪条指令更新？这一条指令对哪些位作了定义？

| 标志 | 位 | 本章含义 |
|---|---|---|
| CF | 0 | 加法进位或减法借位 |
| PF | 2 | 结果低 8 位中 1 的个数是否为偶数 |
| AF | 4 | 位 3 到位 4 的进位/借位 |
| ZF | 6 | 截断后的结果是否为零 |
| SF | 7 | 结果位 15，也就是符号位 |
| OF | 11 | 有符号结果是否越界 |

### 6.1 ZF 和 SF：直接观察结果，但不要过度解释

ZF 观察的是写入位宽内的结果是否为零，不是完整数学结果是否为零。FFFFh+1 的 full 是 10000h，但截断结果为零，所以 ZF=1。若只在截断前检查 full，就会把 ZF 写错。

SF 复制结果的符号位。在 16 位操作里看的是位 15，不是宿主 Number 的正负号。因此 result=8000h 虽然作为 JavaScript 数值是正的 32768，客体 SF 仍然是 1。它告诉软件位模式的最高位是什么，软件采用补码解释时才把它联系到正负。

### 6.2 PF：为何只数低字节

PF 只看低字节，不是整个 16 位结果。例如 8000h 的低字节是 00h，有零个 1，所以 PF=1；0080h 的低字节有一个 1，所以 PF=0。

这条规则并不随着寄存器变宽就自动扩展。只数低八位是 x86 的架构约定，不是我们认定“八位比十六位更有道理”。第一次学习时，把它当成需要遵守的接口定义即可；不要为每个历史约定勉强推导一个现代用途。

“零个一”也是偶数个，所以结果低字节为零时 PF=1。实验中的 0000h 与 8000h 虽然 SF 不同，PF 却相同；0000h 与 0080h 的 SF 都是零，PF 却不同。这样的对比能帮助你看到不同标志观察的是结果的不同部分。

### 6.3 AF：低四位中的进位和借位

AF 在加减法中的实现是：

```ts
const auxiliary = ((left ^ right ^ result) & 0x10) !== 0;
```

本章暂不实现十进制调整指令，但把 AF 纳入加减法测试，避免只检查常用的 CF/ZF。

例如 000Fh+1，低四位从 1111 变成 0000，并向下一位送出进位，所以 AF=1；整个 16 位结果只是 0010h，并没有越界，因此 CF=0。AF 与 CF 的区别不是“一个准确、一个辅助”，而是观察了不同位界。

AF 与早期十进制调整指令有关：按四位存一个十进制数字时，低位数字越过边界的信息对调整有用。我们以后可以再解释具体调整，但这里先实现规则，是为了使加减逻辑的行为完整，而不是要求每个实验都用到 AF。

### 6.4 更新标志不是把整个 FLAGS 清空

算术只更新这六位，其他已建模位保留。例如 FLAGS 的固定位 1 继续为 1。

核心先用掩码清除这次要重新计算的位，再把新值组合进去。这样不会顺便改掉其他职责的位。完整 CPU 的 FLAGS 还包含控制中断、方向等状态；将来补上它们时，一条普通 ADD 不能无意间改变机器的中断控制。

阅读代码时，可以把这一步分成“保留谁”和“更新谁”两个问题。它与前面把立即数的两个字节拼在一起都使用按位或，但含义不同：这里是在合并不同条件位的结果，而不是形成一个 16 位操作数。

## 7. CMP 是做减法，但不写回

为什么需要一条不保存结果的减法？因为程序常常只想知道两个数的关系，却仍要保留原来的值。如果用 SUB 代替比较，检查完 AX 是否等于 3 之后，AX 自身可能已经被减掉，后续代码还得恢复它。

```asm
mov ax, 3
cmp ax, 3
hlt
```

CMP 计算 3-3 并更新标志，因此 ZF=1。但 AX 仍然是 3。

核心中 ADD/SUB 将结果写回，CMP 仅调用减法标志计算：

```ts
case 0x3d:
  arithmetic(left, right, true);
  break;
```

“比较”不是 CPU 返回一个 JavaScript boolean。它把比较信息留在 FLAGS 中，后续条件跳转再读取这些位。

如果两项相等，减法结果为零，ZF 就足以表示相等。但“大于”和“小于”还涉及采用哪种数值解释。无符号的借位可以由 CF 判断；有符号比较则不能单看 SF，因为减法可能溢出，需要结合 SF 与 OF。

例如比较 8000h 和 0001h。按无符号解释，32768 大于 1；按有符号解释，-32768 小于 1。同一次 CMP 可以为这两种判断准备标志，后续程序选择相应的条件。不是 CMP 在同一次执行中给出了矛盾结果，而是软件向它提出了两种不同的问题。

还有一个实践上很重要的限制：比较信息可能被后面的算术覆盖。如果 CMP 后执行 ADD，再根据标志决定分支，分支看到的通常已经不是刚才的比较结果。MOV 在本章不修改标志，所以它又属于另一种情况。以后阅读汇编时，要追踪标志的最近来源，不能只在上面几行找到一个 CMP 就假定联系成立。

## 8. 逻辑操作与未定义标志

AND 逐位取交集，OR 逐位合并，XOR 逐位检测不同。

算术把一组位当作一个数来运算，逻辑操作则可以让我们逐个处理位。例如设备状态常把“是否准备好”“是否有错误”放在不同位，程序需要选出其中一部分；图形或权限数据也常使用位组合。它们并不是脱离计算机组成的数学技巧，而是操作硬件接口的基础工具。

AND 可以保留掩码中为一的位，并清除其他位；OR 可以把指定位置一；XOR 可以翻转指定位置。这里的“位”指二进制位置，不是十六进制字符。操作一个十六进制数字，只是一次同时描述四个位。

```asm
mov ax, 0F0h
and ax, 0Fh   ; AX=0000
or ax, 80h    ; AX=0080
xor ax, 80h   ; AX=0000
hlt
```

这三种指令更新 PF/ZF/SF，清除 CF/OF，但架构没有定义 AF 的结果。本教学核心选择保留 AF，**不能把“保留 AF”当成对真 CPU 的保证**。

逐步看这个例子：00F0h 与 000Fh 没有重叠的一位，AND 后得到零；OR 0080h 使位 7 为一，得到 0080h；再 XOR 同一个掩码，那一位从一翻回零。每一步都发生在 AX 的位模式上，不需要 BIOS 或操作系统解释这些位。

结果为 0080h 时，很多人会因看到最高一个十六进制数字的 8 而误认为 SF=1。但本章是 16 位操作，符号位在 8000h，不在 0080h。前面的两个零不是显示装饰，它们提醒我们当前结果的位宽。

### 8.1 “未定义”不是随机，也不是允许软件假定不变

架构未定义某个标志，表示正确的软件不能依赖这条指令对它给出特定值。某台处理器、某段模拟实现可能总留下同一个值，也可能按某种内部计算改变它；这种观察不自动成为所有兼容实现都应保证的接口。

因此，“本教学核心保留 AF”只是实现选择，不是这一节又发明了一条指令规则。完整项目若为了兼容真机细节采取不同值，也不必因此修改本章逻辑指令的测试目标。我们需要把“明确规定的行为”和“恰好观察到的行为”分开。

所以算术断言使用掩码 08D5h，逻辑断言使用 08C5h，后者排除 AF。对照完整 CPU 时也使用这种规则。

这里的掩码是在选择需要比较的位。与它按位相与之后，不参与契约的位被置零，只剩下本次验证关心的条件。这不是在隐藏错误：如果该定义的 CF、OF 或 ZF 不对，仍然会失败；只是我们不要求双方对未定义 AF 达成不存在的架构保证。

这说明正确性验证不是“所有内部值必须相等”，而是“定义了哪些行为，就验证哪些行为”。

## 9. 实验：把预测落实成每一步断言

打开 [第 4 章实验页](../../teaching/ch04/index.html)。每个实验都提供可修改机器码、可读汇编、检查点和实际执行记录。

每个实验都先执行一条 MOV，再执行待观察的运算，最后 HLT。这个安排有明确目的：MOV 建立已知输入且不改标志，运算体现本次规则，HLT 给出稳定终点。你不用猜测 AX 是从哪个旧程序留下的，也不用在其他操作不断覆盖 FLAGS 时抢着观察。

下面列出的标志数值是用于自动检查的合并结果，不建议直接死记。先把各位应为零还是一写出来，再按表中的位置合并，最后与实验面板核对。这样，数值可以帮助你验证推理，而不是替代推理。

### 9.1 无符号进位

```text
B8 FF FF 05 01 00 F4
```

两步后 AX=0000h，CF/PF/AF/ZF=1，SF/OF=0。算术位掩码后的值为 0055h。

其中 CF 来自 full 超出 FFFFh，ZF 来自截断结果为零，AF 来自低四位越界，PF 来自低字节中有偶数个一。它们虽然在一个 FLAGS 数值里同时出现，却各有自己的原因。解释完整的结果，应把这些原因分开说出来。

### 9.2 有符号溢出

```text
B8 FF 7F 05 01 00 F4
```

两步后 AX=8000h，PF/AF/SF/OF=1，CF/ZF=0。掩码后的值为 0894h。

结果低字节依然为零，所以 PF=1；结果符号位为一，所以 SF=1；两个正数输入的结果变成负数位模式，所以 OF=1。CF 却为零，因为按无符号输入计算的 full 只有 8000h，没有跨过 16 位上界。

先自己预测，比较两个实验中 CF 和 OF。它们不是同一个“溢出”位。

### 9.3 借位

```text
B8 00 00 2D 01 00 F4
```

两步后 AX=FFFFh，CF/PF/AF/SF=1，ZF/OF=0，掩码后为 0095h。按有符号解释，0-1 并没有越界。

把这一项与前一项放在一起，可以看到 SF=1 既可能伴随 OF=1，也可能伴随 OF=0。符号位只是结果的一部分，是否溢出还要回到输入和位宽判断。

### 9.4 只更新比较信息

```text
B8 03 00 3D 03 00 F4
```

两步后 AX=3，PF/ZF=1，其他算术标志为 0。掩码后为 0044h。这个断言能抓住把 CMP 错误写成 SUB 的实现。

本次尤其要同时看 AX 与 ZF。只看 ZF=1，错误的 SUB 实现也可能“通过”；只看 AX=3，却无法证明减法条件真的计算过。两个观察点一起检查，才体现 CMP 的完整职责：产生比较信息，同时保留操作数。

### 9.5 位操作

逐步验证 AX 为 00F0h、0000h、0080h、0000h。AF 不参加本实验的真机对照。

观察模块可随时卸载，重新装载并执行同一个实验，断言仍应通过。

如果你目前还不能解释每个位，不必先去改实现。把输入、full、result 和标志的理由依次写下来，通常就能找到断开的那一环。调试工具显示的是结果，理解则需要把结果重新连接到规则和输入。

## 10. 故意破坏一个环节

### 10.1 程序变了，原来的预期必须失败

在“有符号溢出”实验中把 `B8 FF 7F` 改为 `B8 FF FF`，装载并运行，但仍使用原实验断言。

这时真实执行得到 AX=0、CF=1、OF=0。原来的 AX=8000h、OF=1 检查应失败。这不是核心错误，是输入不再满足这个实验的前提。

### 10.2 ALU 会比较，不代表 CPU 已会分支

选择 `EB FE`，也就是 `JMP $`。本章应报告操作码 EB 未实现，不从完整项目导入跳转逻辑。

### 10.3 修改核心验证断言的价值

在本地源码把 CMP 改成写回减法结果，再运行测试。“CMP：只改标志”应失败。恢复修改后再次运行。

也可以把 OF 总置为零；有符号溢出测试应失败，而仅观察 FFFFh+1 的实验可能无法发现这个错误。

这解释了为什么需要少量有区分力的断言，而不是重复几十次“运行到 HLT”。

失败实验还帮助区分两种常见问题。修改应用字节后，核心正确执行却不再符合原来的预期，这是实验前提变了；修改 OF 公式后，原输入不变而结果违反规定，这是核心实现变错了。两者都可能表现为断言失败，但定位方向完全不同。

## 11. 状态不变量与自动化检查

本章测试位于 [tests/core.test.ts](../../teaching/ch04/tests/core.test.ts)，固定实验位于 [experiments.ts](../../teaching/ch04/src/experiments.ts)。

持续保持：

- AX 和其他寄存器保持 16 位值。
- 非目标寄存器不因 AX 运算改变。
- 查看状态和内存不会执行程序，也不会消费客体数据。
- 未完成的立即数不修改 AX 或 FLAGS。

操作契约：

- 所有本章新增指令消费三个字节。
- ADD/SUB 的结果等于数学结果的低 16 位。
- 标志符合位宽和有符号/无符号规则。
- CMP 不写回。
- 逻辑运算清 CF/OF，未定义 AF 不成为对照断言。
- 前一章 MOV/HLT 仍可执行。

测试还检查 8000h-1 的减法溢出，防止只有加法路径正确。

选择测试输入时，应让不同错误产生不同结果。两个小正数相加通常无法检查 CF 或 OF，结果低字节总为零也很难发现 PF 计算范围错了。边界值并不是为了刻意刁难实现，而是让规则中容易被混淆的部分真正参与一次运算。

同时，不必把内部函数的拆分写进断言。一个核心用公共算术函数，另一个用分开的加法与减法路径，都可以正确。我们要验证的是指令所承诺的状态变化，不是作者偏好的代码形状。

## 12. 核心为什么与演示代码分开

本章核心只引用共享的 TypeScript 类型，不引用 DOM、宿主、完整 CPU 或上一章源码。

```text
实验数组 → 宿主装载和单步 → CPU 核心
                              ↓
                    只读状态和本次执行结果
                              ↓
                         可选观察模块
```

`state()` 返回冻结的状态副本；`peek()` 返回内存副本。观察模块保存最近 100 步轨迹，核心不维护网页追踪历史。

轨迹来自每次真正成功执行的 `step()` 结果，而非播放预先编好的指令列表。对教学错误，界面显示错误状态，不伪造成功记录。

本章没有为速度引入标志惰性计算、取指窗口或事件快路径。工程核心即使结构完全不同，只要满足本章已定义行为，就可以作为对照。

这也是教学中值得坚持的顺序：先让每个状态值的来源都能直接找到，再讨论如何少做重复工作。如果第一次阅读就要同时理解缓存是否有效、标志何时真正计算和哪个快路径被选中，往往很难判断一个数究竟来自当前指令还是旧状态。

清楚的简单实现不是最终工程的障碍，而是后续优化的参照物。优化之后仍能按同样输入检查已定义结果，才有依据说“做得更快，但没有改变意思”。

## 13. 完整平台对照

启动页选择对应教学实验，进入关闭全部设备、BIOS/DOS 的直接调试环境。

源码通过带助记符注释的 DB 行提供与实验相同的指令字节。COM 入口为 0100h，所以本章 IP=3 对应完整平台 IP=0103h。

同一个 ADD 助记符可以有不同编码。完整项目的汇编器会把小立即数自动编码为 83h/ModR/M 形式，本章还没有实现它；这里明确提供 AX 专用操作码，不修改汇编器的正常行为，也不假装助记符只有一种机器码。

使用算术或逻辑掩码比较 FLAGS，不能因完整 8088 的保留位或未定义 AF 差异判定错误。完整平台还设置了装载布局与堆栈，但本章程序不使用它们。

自动对照测试在 [teaching.test.ts](../../tests/teaching.test.ts)：对成功实验逐条执行两种核心，比较已定义寄存器、IP、停机和标志，并验证完整汇编器生成的字节。独立核心的失败边界不作为完整 CPU 的共同契约。

同题对照时，先确认两边究竟装载了哪些字节，而不只确认助记符相同。编码、初始条件和检查范围一致以后，差异才更容易解释为实现问题；否则可能只是两个实验根本没有在检验同一条路径。

## 14. 古今对照：ALU 和 FLAGS 并没有消失

在 x64 Windows 11/Linux 中：

- ADD、SUB、CMP、AND、OR、XOR 和 CF/ZF/SF/OF 等标志仍然使用。
- 可使用更宽的寄存器；实际操作数宽度由模式、编码和前缀决定。
- 软件仍须区分有符号和无符号比较；类型不直接写在普通 ADD 的输入位模式中。
- 编译器可能选择其他指令完成同样工作，不代表基础机制消失。
- SIMD 指令提供另一类并行数据操作，不能默认所有算术都采用本章的 FLAGS 更新方式。
- 现代 CPU 内部可能使用重命名、乱序执行、标志相关优化，但对软件仍须遵守架构定义的结果。

参考：[Intel 架构手册入口](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)。查指令时同时阅读操作数宽度、标志影响、异常和模式约束。

回到现代程序时，本章最值得迁移的不是一张 16 位标志数值表，而是三个习惯：确认运算宽度，区分位模式与数值解释，追踪条件信息最近由谁更新。它们对阅读编译器生成的代码、判断整数边界和理解硬件寄存器都仍然有用。
