# 第 2 章：数字如何进入机器

> 本章目标：从同一块字节内存出发，弄清进制、位宽、补码、小端序和截断。新增两字节的小端读写；仍然没有 CPU、指令执行或 ALU。
>
> 配套工程：[ch02](../../teaching/ch02/README.md)。在完整项目启动开发服务器后，打开 `/teaching/ch02/index.html`。第一章的所有字节行为仍然保留。

## 1. 内存保存了 41h，然后呢

上一章，我们在内存中写入了 `41h`。观察窗口可以显示十进制 65，也可以显示二进制 `01000001`。如果使用 ASCII 编码解释，它还可以代表字符 `A`。

这几个结果很容易引出一个误解：内存是否同时保存了十进制数、十六进制数和字符？答案是否定的。这里保存的只是八个位。不同写法和不同意义，是读取者对这八个位作出的解释。

如果我们在一个十六进制编辑器里把文件中的 `41` 改成 `42`，一个文本程序可能显示 `B`，另一个程序可能把它当作数量 66，还有一个程序可能在文件格式检查时报告错误。它们并没有读到不同的内存内容；它们使用了不同规则。

这一章的主线就是把几种常被混在一起的问题分开：

- **进制**回答怎样写出同一个数。
- **位宽**回答允许保存多少个位，以及有多少种位模式。
- **有符号解释**回答怎样把位模式映射到正数和负数。
- **字节序**回答多个字节怎样组合成较宽的数。
- **字符编码**回答某些数值怎样对应字符。

这些不是五种不同的内存。它们是我们在同一份存储之上使用的规则。CPU 将来也会按指令规定采用其中一些规则，软件则会根据类型、协议和用途选择其他规则。

## 2. 从位到字节：先看位置权重

### 2.1 二进制不是另一种数学

十进制数 123 的意思是：

```text
1 × 100 + 2 × 10 + 3 × 1
```

每向左移动一个位置，权重乘以 10。二进制使用同一个位置计数思想，只是每个位置只能取 0 或 1，向左的权重乘以 2。

以八位模式 `01000001` 为例，从右到左的权重为：

```text
位：    7   6   5   4   3   2   1   0
权重：128  64  32  16   8   4   2   1
取值：  0   1   0   0   0   0   0   1

结果 = 64 + 1 = 65
```

这里的位编号从 0 开始，最低位是第 0 位。我们通常把最高位写在左边，只是一种书写习惯；它不自动规定内存地址顺序，也不自动规定串行传输时先发送哪个位。

当我们说“把某个位设为 1”，指的是改变位模式中的一个位置；当我们说“加一”，指的是对解释出的数作运算。这两种动作有时效果相似，但不是同一个概念。例如，把 `00000001` 的最低位再设为 1，结果仍为 1；给数值 1 加一，结果是 2。

### 2.2 为什么八个位有 256 种模式

每个位有两种选择。八个位组合起来有 `2^8 = 256` 种可能。如果全部按无符号整数解释，就从 0 到 255。

最大值不是 256，因为零也占了一种模式。八位全为 1 时：

```text
128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = 255
```

这个结论可以推广到 n 位：有 `2^n` 种模式，无符号范围是 `0` 到 `2^n - 1`。16 位有 65,536 种模式，最大无符号值为 65,535。

第一章的内存地址也恰好从 0 到 65,535，但不要把两个范围相同误认为它们是一回事。地址范围由模型容量和寻址接口决定；一个位置的内容范围由存储单位决定。本章每个地址依然只保存一个八位字节。

## 3. 十六进制：给位模式换一种方便的写法

### 3.1 四个位对应一个十六进制数字

十六进制每位有 16 种取值，用 `0`～`9` 和 `A`～`F` 表示。因为 `16 = 2^4`，每四个二进制位正好可以写成一个十六进制数字。

```text
0100 0001
  4    1

01000001₂ = 41h = 0x41 = 65（十进制）
```

这就是为什么阅读机器码和内存转储时常用十六进制。它比二进制短，又能清楚对应位组。八位字节写成两个十六进制数字，16 位值写成四个，32 位值写成八个。

注意，字符串 `41` 本身没有把进制说清楚。本书文字中的 `41h` 表示十六进制，代码中的 `0x41` 也表示十六进制；未标注的日常数字一般按十进制理解。写实验输入时不要依赖“看起来像机器码所以应该是十六进制”。

本章手工输入接受以下完整写法：

```text
65
0x41
0b01000001
```

三者解析后得到同一个宿主整数。解析器不会把 `65abc` 的前半段悄悄当作 65，也不会把 `0b102` 当作有效二进制。它必须先确认整个输入格式合法，再转换数值。这个限制属于宿主实验接口，不是 CPU 解析了文本。

### 3.2 前导零说明宽度，不改变数值

`0x41` 与 `0x0041` 作为非负数学整数都等于 65。但把它们写成两个或四个十六进制数字，可以提示我们正在讨论八位还是 16 位模式。

这种提示并不让 TypeScript 字面量自动具有对应位宽。宿主的普通 `number` 不会因为写了四个十六进制数字，就变成客体 16 位寄存器。宽度必须由接口检查和运算规则明确落实。

这个问题在模拟器里非常重要。我们使用的宿主语言，与被模拟 CPU 的数值规则不是同一套。如果依赖宿主自动决定范围，客体寄存器可能意外保存 65,536，或者某个宿主位运算把较宽值转换成 32 位。能够正确运行几个小数值，不代表位宽已经正确实现。

## 4. 位宽：不是数字后面的装饰

### 4.1 数学结果与可保存结果

在普通数学里，255 加 1 等于 256，不需要再问它能否放进一个字节。但如果结果只能保留八个位，256 的二进制表示就多出一个位置：

```text
  11111111   255
+ 00000001     1
-----------
1 00000000   256
  ^^^^^^^^   保留低 8 位为 0
```

这不是加法“算错了”，而是存储结果只能包含指定数量的位。我们应同时描述数学结果为 256、保留低八位后为 0，以及数学结果已超出八位无符号范围。

如果结果宽度为 16 位，同一组输入就可以保存为 `0100h`，即 256，不会超出 16 位无符号范围。因此，“是否溢出”必须说明相对于哪个范围。没有位宽和解释方式，单说“这个加法溢出了”是不完整的。

对于本章使用的非负整数，保留低 n 位可以写成：

```text
低位结果 = 数学结果 mod 2^n
```

例如 `65536 mod 65536 = 0`。这个式子是解释结果的数学关系。本章的示范由宿主计算，不是已经造出了 ALU。

### 4.2 截断应当发生在定义它的地方

第一章的 `write8(0, 256)` 报错，本章却说“八位加法结果可保留为零”。这两句话并不矛盾。

前者是内存 API：调用者要写入一个已经合法的字节。后者是固定宽度运算：先完成数学运算，再根据已定义规则提取结果位。若将来实现 CPU 的八位加法，CPU 应把保留后的值和标志位准备好，再提交到相应状态中。

我们不会把这条规则暗中藏在内存数组的自动转换中。否则，在调试时，既不能区分错误输入与正确截断，也不能判断运算相关的标志究竟在哪里产生。

还有一个边界：本章数学示范的两个输入都按无符号位模式检查，结果用非负整数取模。不能把这个有限接口直接当作对任意负数或任意大整数都适用的语言工具。对更宽整数和负数取模，需要继续明确宿主表示范围和规范化规则。

## 5. 补码：同一组位如何表示负数

### 5.1 位模式不带“signed”标签

看到八位 `11111111`，我们已经知道它有 256 种模式中的最后一种。按无符号解释，它是 255。若按八位补码解释，它是 -1。

存储中的位没有变化，也没有额外的符号标签。不同的是解释规则。程序的类型、所用指令或协议字段会决定采用哪种规则。

这也是为什么“最高位是 1，所以这是负数”缺少前提。应当说：“在指定宽度的补码解释下，最高位为 1 的模式代表负数。”对于无符号数，它只是较大的权重位；对于字符或位掩码，它可能根本不对应正负问题。

### 5.2 用映射公式理解补码

先把 n 位模式按无符号读成整数 `u`。补码解释可以定义为：

```text
若 u < 2^(n-1)：有符号值 = u
否则：          有符号值 = u - 2^n
```

以八位为例，0～127 仍表示自己；128～255 分别解释为 -128～-1。

```text
00h =   0 ->    0
7Fh = 127 ->  127
80h = 128 -> -128  （128 - 256）
FFh = 255 ->   -1  （255 - 256）
```

这样不是给每个负数附加一个符号位再保留七位绝对值，而是把一半模式整体重新映射为负数。八位补码范围因此为 -128～127。

负数数量比正数多一个，不是实现遗漏。共有 256 种模式，非负侧的 128 种包括零，剩下 128 种表示负数。只有一个零，最负值没有对应的同宽正值。

16 位补码使用相同规则，范围为 -32,768～32,767。`8000h` 解释为 -32,768，而不是 -0；`FFFFh` 解释为 -1。

### 5.3 为什么“取反加一”能得到负数模式

对于非零、范围内的正数 x，它的负数在 n 位补码中的模式是 `2^n - x`。按位取反会得到 `(2^n - 1) - x`，再加一恰好得到前面的结果。

```text
8 位的 +1：00000001
按位取反：11111110
再加一：  11111111  -> 按 8 位补码解释为 -1
```

这样，“取反加一”就不再是一条孤立口诀，而是固定宽度映射的结果。其成立依赖于规定了宽度；如果没有说明在哪 n 位内取反，就无法确定得到哪个模式。

补码还使许多加减法可以共享低位运算机制：

```text
FFh + 01h = 100h
保留低 8 位 -> 00h
```

按无符号理解，这是 255 加 1 后超出范围；按八位补码理解，这是 -1 加 1 得到 0，结果在有符号范围内。低八位相同，但“是否超出范围”的判断不同。第四章会把这一区别落实为 CPU 的 CF 和 OF，而不是本章就偷偷计算 FLAGS。

### 5.4 宽度改变，解释也可能改变

八位 `FFh` 是 -1；16 位 `00FFh` 却是 255。原因不是补码规则变了，而是宽度从 8 变为 16，最高位的位置和映射范围都变了。

若希望把八位 -1 扩展为仍代表 -1 的 16 位模式，就应得到 `FFFFh`，也就是复制符号位进行符号扩展。若希望保留无符号 255 的意义，则应得到 `00FFh`，也就是零扩展。

```text
原始 8 位：   FF
零扩展为 16：00FF -> 255
符号扩展为16：FFFF -> -1
```

这两种扩展都可以是合理操作，但用途不同。现在我们只解释它们，尚未实现对应 CPU 指令。以后读取一个较窄字段再参与较宽运算时，要明确是谁选择扩展方式：指令语义、编译器生成的代码，还是程序员定义的协议规则。

## 6. 小端序：一个 16 位数要占两个地址

### 6.1 从 1234h 拆出两个字节

一个字节最多保存 `FFh`，不能把 `1234h` 原样放进一个位置。16 位值需要两个字节。

```text
1234h = 12h × 256 + 34h
高字节 = 12h
低字节 = 34h
```

x86 的普通多字节整数存储采用小端序：低字节放在低地址。若起始地址为 `0010h`：

```text
地址    内容
0010h   34h   低字节
0011h   12h   高字节
```

我们在纸上通常把数的高位写在左边，内存转储却通常按地址递增从左到右显示，所以转储会呈现 `34 12`。这不是 CPU 把数字搞反，而是书写数值和展示地址用了不同顺序。

### 6.2 内存本身不会识别“高字节”

内存核心中的每个位置仍然只保存一个字节。将地址 16 的 `34h` 与地址 17 的 `12h` 组成 `1234h`，是读取函数采用的小端规则。

如果读取者使用大端规则，同样两字节会得到 `3412h`。大端把高字节放在低地址，网络协议中的多字节字段经常采用这种约定。没有一种规则使底层字节获得额外的“高”“低”标记。

因此，讨论字节序必须针对多字节对象及其解释。单独一个字节不存在这层字节顺序问题；字符串 `"AB"` 的字符顺序也不是把一个 16 位整数的小端序生搬硬套过来的。

现代 Unicode 文本还要区分具体编码：UTF-8 使用字节序列表示字符，不应把它简单解释成“小端字符数组”；UTF-16 的代码单元若序列化为字节，则要明确字节序。字符编码、代码单元和多字节整数规则是相邻知识，不是同一个概念。

### 6.3 本章新增的读取代码

[第二章核心](../../teaching/ch02/src/core.ts)保留第一章的字节接口，新增 `read16LE` 与 `write16LE`。`LE` 是 little-endian，主动把规则写进名字。

```ts
read16LE(address: number): number {
  this.checkAddress(address);
  this.checkAddress(address + 1);
  return this.bytes[address] | (this.bytes[address + 1] << 8);
}
```

先读取低字节，再把高字节左移八位，最后组合。两部分在目标 16 位结果中不重叠，所以这里按位或与相加得到相同结果。

`<< 8` 不是把内存中的字节移到另一个地址，而是在宿主计算中把高字节放到结果的高八位。数据位置的移动与数值位移又是两个不同操作。

JavaScript 的这些位运算会使用 32 位整数规则；这里每个输入已是合法字节，组合结果最多为 65,535，使用它们不会破坏本章的 16 位无符号结果。但以后模拟更宽数据时，不能盲目复制这段代码，假设宿主位运算天然等于任意宽度的客体运算。

### 6.4 写入之前，先检查整个操作

写入代码把低八位与高八位分别保存：

```ts
write16LE(address: number, value: number): void {
  this.checkAddress(address);
  this.checkAddress(address + 1);
  if (!Number.isInteger(value) || value < 0 || value > 0xffff) {
    throw new Error('16 位值必须位于 0～65535');
  }
  this.bytes[address] = value & 0xff;
  this.bytes[address + 1] = value >>> 8;
}
```

`value & 0xff` 提取低字节；`value >>> 8` 把高字节移到最低八位。本章已经验证 value 不超过 16 位，所以后者最多为 255。

这里有一个比拆字节更容易忽略的细节：两个地址和整个数值都检查通过以后，才提交第一个字节。如果先写低字节，再检查第二个地址，那么在地址 `FFFFh` 写 16 位值时，操作可能写了一半才失败。

我们的 API 要求失败后整块内存不变，因此必须先检查完整范围。这个保证属于本章宿主 API，不是关于真实 CPU 访存原子性、总线周期或跨页故障行为的通用结论。那些问题必须结合具体机制讨论。

本章允许从奇数地址读写两个字节，也就是不强制两字节对齐。它不模拟对齐相关时序或性能差异。两个地址必须都在这块数组中，`FFFFh` 不会悄悄回绕到 0；以后实现体系结构地址计算时，再在对应层引入地址规则。

## 7. 数据、地址、字符和指令：四种角色

### 7.1 同样是数字，角色不同

假设地址 `0010h` 中保存了 `34h`。这里的 `0010h` 是选择位置的地址，`34h` 是该位置的内容。用 `read16LE(0x10)` 读出 `1234h` 以后，`1234h` 是读取结果，不会自动成为下一次访问地址。

只有当后续程序把这个数当作地址使用，它才进入“指针”的角色。内存并没有自动沿着数值追踪另一个位置。

同样，`41h` 只有在某个读取者按字符编码解释时才表示 `A`。若读取者把它作为计数，就意味着 65。真实 CPU 的普通内存并不检查我们是否把整数误当作字符或地址；软件需要通过类型、接口和协议守住这些意义。

### 7.2 机器码也不能脱离上下文

第三章会使用 `B8 34 12` 作为一条指令的字节。在对应的 16 位编码上下文中，`B8` 指定一种操作，后面的 `34 12` 是按小端组合的立即数 `1234h`。

但是本章把这三个字节写进内存以后，它们仍然不会执行。我们只具备存储与组合数值的规则，没有 IP，也没有取指循环。

这为下一章准备了一个非常具体的问题：CPU 应如何识别第一个字节，又应如何决定接下来两个字节属于立即数而不是另外两条指令？答案来自指令编码规则和取指状态，不来自内存自己识别“程序”。

## 8. 实验：先预测，再检查实际数值

本章实验继续使用宿主操作列表。记录区出现“宿主解释”或“宿主数学演示”时，请按这个归属理解：这些工具帮助我们解释数字，但没有替未来 CPU 实现隐藏的指令。

### 实验一：同一个字节，三种写法

选择“同一个字节，三种写法”。预期地址 0 保存 `41h`，观察记录给出二进制 `01000001`，无符号和八位补码解释均为 65。

然后手工在同一地址分别输入 `65`、`0x41`、`0b01000001`。每次写入后观察结果应相同。这里是三个文本输入经过宿主解析得到同一个值，不是内存保存了三份编码。

手工修改会使原实验验收失效。请重置后再执行自动操作，而不是把不同输入混入同一组预期。

### 实验二：低字节在低地址

选择“低字节在低地址”。实验在地址 `0010h` 写入 `1234h`，检查原始字节，再按 LE 规则读取：

| 操作 | 原始字节 / 读取结果 |
|---|---|
| write16LE(10h, 1234h) | 10h 为 34h，11h 为 12h |
| read16LE(10h) | 1234h |
| 手工顺序改为 12h、34h | 两个字节的内容交换 |
| read16LE(10h) | 3412h |

注意第二次读取使用的函数没有变。数值变化来自数据位置变化，而不是读取者临时猜测了另一种字节序。

这个实验的断言既检查写后读回，也检查原始字节顺序。只检查“写入后能读回相同值”不够：如果读写两个函数同时错误地采用大端，它们仍可能互相抵消并通过往返检查。

### 实验三：FF 是 255 还是 -1

选择“补码：位模式不自带类型”。在查看实际输出前，先填写：

| 位宽 | 模式 | 无符号解释 | 补码解释 |
|---|---|---|---|
| 8 | FFh | 255 | -1 |
| 16 | 00FFh | 255 | 255 |
| 16 | FFFFh | 65535 | -1 |
| 16 | 8000h | 32768 | -32768 |
| 16 | 7FFFh | 32767 | 32767 |

第二章页面还提供“位模式解释”工具。输入必须是当前位宽内的非负位模式，例如要观察八位 -1，请输入 `0xFF`，而不是给字节存储接口写入 -1。

工具展示二进制、十六进制、有符号和无符号结果，不修改内存。它提供的是不同解释之间的对照，不是一条“把内存切换到 signed 模式”的命令。

### 实验四：相同加法，不同位宽

选择“位宽与截断：先用宿主数学理解”。

| 输入和结果宽度 | 数学结果 | 保留后的值 | 超出该无符号范围 |
|---|---|---|---|
| 255+1，8 位 | 256 | 0 | 是 |
| 255+1，16 位 | 256 | 256 | 否 |
| 65535+1，16 位 | 65536 | 0 | 是 |

不变量分别检查低位结果和无符号越界判断，而不是只打印一行算式。实验仍不执行 ADD，也不产生 FLAGS。以后我们需要把运算、标志和状态提交一起实现，才能说 CPU 已具备这项能力。

### 实验五：最后一个地址还能写两个字节吗

选择“失败实验：两个字节必须都在范围内”。先在地址 `FFFFh` 放入 `5Ah`，再尝试在这里写 `1234h`。

因为第二个地址超出当前数组，写入应明确失败。实验检查整块内存与失败前相同，尤其是末尾字节仍为 `5Ah`，地址 0 也没有因“回绕”被修改。

另外，尝试写入 65,536 也应失败，并保持原内存。这再次区分了“输入超范围”和“已定义运算结果截断”。本章不把 API 的错误提示伪装为 x86 的客体异常。

## 9. 固定断言：怎样证明不是碰巧看起来正确

本章的验收分成几类，每类对应不同错误：

- 字节行为保持：第二章仍满足第一章所有实验，不能为了两字节读写破坏单字节边界。
- 字节序：`1234h` 必须实际存为 `34 12`，不能仅用读写互相验证。
- 访问范围：合法的两字节操作只影响相邻两个字节；非对齐地址也按本章约定工作。
- 解释宽度：`FFh` 的八位补码为 -1，16 位 `00FFh` 的补码为 255。
- 截断：低位结果和无符号范围判断同时符合预期。
- 失败状态：越界地址和非法数值明确报错，且不提交部分写入。
- 观察隔离：取出的副本及解释结果不成为修改核心状态的暗门。

这些检查位于[本章测试](../../teaching/ch02/tests/memory.test.ts)，跨章保持检查位于[完整项目教学测试](../../tests/teaching.test.ts)。测试没有要求教学核心与完整 CPU 内部组织相同，只要求当前已经定义的行为成立。

关闭观察模块后，实验断言应仍然通过。再安装它，应显示现存内存，而不是恢复某一套预置截图。原始值、解释规则和呈现效果应能分别验证。

## 11. 从 8086 到今天：哪些变了，哪些没变

### 11.1 位宽和补码仍然是基础

8086 常见的整数操作宽度为 8 位和 16 位，80386 引入广泛的 32 位能力，x64 又提供 64 位整数与寻址相关能力。处理器叫“64 位”并不意味着每条指令、每个字段和每次访存都是 64 位；现代软件仍然大量使用八位字节、16 位或 32 位字段。

补码仍是现代 x86 整数有符号解释的基础。无符号与有符号范围的区别也仍然存在。第四章讲的进位和有符号溢出不是已经淘汰的知识，只是现代应用通常通过高级语言间接使用这些机制。

需要补充一个软件层边界：CPU 的固定宽度运算规则，不等于每门语言都允许按相同方式依赖溢出。C/C++ 的无符号整数运算具有规定的模意义，而普通有符号整数溢出属于未定义行为，编译器可以基于“程序不发生这种溢出”的假设进行优化。不能因为 x86 加法会得到低位结果，就推断任意 C 表达式都能安全依赖同一现象。

JavaScript 的 `number` 也不是 x86 的 64 位整数寄存器。它使用浮点数表示，整数精确范围受限；许多位运算还会转换为 32 位。模拟器必须显式管理客体位宽，必要时使用适合更宽整数的表示。

### 11.2 小端序仍然存在，但协议不必相同

x64 普通多字节整数内存表示仍采用小端序，所以观察 `1234h` 存为 `34 12` 并不只是考古知识。Linux 和 Windows 软件读取二进制结构、调试内存或实现文件格式时仍然会遇到它。

但是，主机使用小端，不代表所有网络包、文件字段和外设协议也采用小端。协议的规则由协议定义，应用可能在读写时转换。弄清“数值由谁解释”，在现代数据交换中依然重要。

ASCII 中 `A = 41h` 的对应关系仍广泛存在，也与 UTF-8 的 ASCII 范围兼容。但现代文本不能仅用“一个字节就是一个字符”概括。我们选 ASCII 字符作为贯穿案例，是为了先减少变量，不是把现代字符处理压缩成八位模型。

### 11.3 64KB 是本书的阶段限制，不是现代主流结构

本章 64KB 存储和第三章的 16 位 IP 是教学上的台阶。现代 x64 应用不依赖我们尚未实现的 8086 段:偏移寻址方式来组织一般内存访问；它们通常在操作系统管理的虚拟地址空间中工作。

但“地址选择位置、内容保存位模式、映射由其他层提供”的框架仍然有效。进入分段和分页章节以后，我们会扩大模型，并明确哪些历史规则主要属于旧模式或兼容路径，哪些转换与保护思想仍然构成现代系统的基础。
