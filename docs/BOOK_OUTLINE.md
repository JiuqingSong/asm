# 从一条指令到一台 PC：写作与实验环境总纲

## 1. 文档定位

本文汇总本项目配套书籍及实验环境的目标、内容结构、写作原则、架构边界、交付要求和实施顺序，作为后续写作与开发的共同依据。

- 暂定书名：**《从一条指令到一台 PC：一步一步手搓 8086—80486 虚拟机》**。
- 首要读者：项目作者本人。以能够亲手运行、观察、修改和解释为理解标准，而不是以记住术语为标准。
- 行文面向有一些编程和计算机基础、但对组成原理尚未建立完整理解的读者；不默认读者已熟悉汇编、编码、位宽、标志或软硬件职责之间的联系。
- 本项目是完整实现、实验平台和对照对象；书中的教学实现是另外整理的渐进代码线。
- 本文描述的是目标设计，不代表教学模式、章节代码和观察插件已经实现。
- 已有试验交付：[第 1 章文字稿](book/ch01.md)、[第 2 章文字稿](book/ch02.md)、[第 3 章文字稿](book/ch03.md)、[第 4 章文字稿](book/ch04.md)，以及各章的[状态实验工程](../teaching/ch01/README.md)、[数值与内存工程](../teaching/ch02/README.md)、[第一条指令工程](../teaching/ch03/README.md)、[ALU 工程](../teaching/ch04/README.md)。第一、二章没有 CPU，提供明确标为宿主操作的实验；第三、四章开始执行指令并提供完整平台同题对照。当前并非完整教学模式；尚未提交或发布固定标签。
- 后续工作应先满足本文明确的原则和验收要求，再选择具体实现方案。目录可按样稿反馈调整，不应随意改变职责区分、渐进交付和核心分离原则。

## 2. 书的目的

通过逐步搭建 8086—80486 虚拟机，理解计算机每一层的职责、接口和实现来源，并认识这些机制如何延续或演变为现代计算机。

全书围绕一个问题展开：

> 一段程序，如何从内存中的字节，变成屏幕上的文字、磁盘里的文件和串口线上传出的数据？

读者完成学习后，应能够：

1. 从寄存器、内存和取指循环开始，逐步建立一台可以工作的虚拟 PC。
2. 解释指令执行、寻址、中断、设备通信、启动、保护模式和分页的完整路径。
3. 分清 CPU、设备、固件、操作系统、驱动、应用程序与宿主环境分别提供什么。
4. 找到关键状态、数据和代码的来源，理解谁建立它们、谁使用它们、谁能够修改它们。
5. 在完整平台上观察功能，也能下载章节代码亲手实现和修改功能。
6. 通过正常实验、失败实验和测试验证理解，而不是只依赖“程序好像能运行”。
7. 对照 x64 Windows 11/Linux，判断旧机制的延续、变化、兼容用途和替代技术。

### 2.1 不以什么为目标

- 不写成全部指令、端口和系统调用的百科；完整查表内容由参考手册和附录承担。
- 不按现有源码文件逐行讲解，不把成熟代码直接当成教学顺序。
- 不追求晶体管、电气或精确时钟周期级的整机还原。
- 不将运行 Windows 等真实软件作为每章的必要前提或唯一正确性证明。
- 不在主线中完整实现现代 x64 CPU、Windows/Linux 内核、现代 GPU 或全部 PC 外设。
- 不为了写书立即重构完整项目，也不默认将当前 UI 全部改造成插件体系。

## 3. 贯穿全书的原则

### 3.1 职责归属：机制、策略、数据和代码分别来自哪里

讲述任何功能或关键代码时，应回答：

| 问题 | 必须说明的内容 |
|---|---|
| 规则是谁规定的 | CPU 指令集、设备规范、固件接口，还是软件约定 |
| 状态和参数是谁准备的 | 固件、系统、驱动、应用、设备，还是外部输入 |
| 动作是谁执行的 | CPU、设备控制器，还是某段软件 |
| 执行代码来自哪里 | 固件 ROM、系统文件、驱动、应用，还是运行时生成 |
| 策略由谁决定 | 权限、分配、调度、缓冲和错误恢复等决策的制定者 |
| 本项目如何模拟 | 对应核心、设备模型、高层替代或宿主适配 |

固定强调：

> CPU 执行了一段代码，不等于这段功能是 CPU 自带的；操作系统配置了硬件，不等于动作全部由软件执行。

“写死在 CPU 中”应解释为由 CPU 架构规定、由内部硬件或微码实现的行为，不暗示每条指令都有独立硬接线电路。

具体要求：

- 区分固定行为与可配置内容。例如 INT 的控制转移机制由 CPU 提供，中断入口和服务参数约定由软件建立。
- 不凭中断号认定处理程序来源。应追踪当前向量、目标地址、目标代码以及安装或替换入口的软件。
- 区分代码最初来源与当前存放位置。ROM 代码可能复制到 RAM，系统代码可能经分页映射。
- 区分 CPU 的保护机制与操作系统的保护策略。例如 CPU 检查页权限，操作系统建立页表并处理缺页。
- 书中出现模拟器专有陷阱、观察钩子、装载便利或调试写入时，明确标为宿主提供的教学/模拟能力。
- 观察界面提供调试写入能力，不代表客体应用具有对应的硬件访问权限。

### 3.2 古今对照：这项技术今天在哪里

每项主要技术应以普通 x64 Windows 11/Linux 系统为基准，按以下类别说明：

1. 仍是核心机制。
2. 仍存在，但用途或实现形式改变。
3. 主要用于兼容或特定场景。
4. 已退出现代桌面 PC 主流。

每章对照至少回答：保留了什么、改变了什么、主要由什么接替、为什么改变。

- 分开讨论具体芯片、接口和设计思想。例如 8237 退出主流，不代表 DMA 思想过时。
- 分开讨论 CPU 支持、操作系统支持和普通应用可用能力。
- 不将接替关系简化为一对一替换。例如 MSI/MSI-X 与 APIC 分属中断体系的不同环节。
- 标明适用模式和场景。例如长模式中的 64 位代码与兼容模式不能混为一谈。
- 现代对照保持为短小独立小节，详细实现交给扩展阅读，不冲淡历史机器搭建主线。
- 事实性断言应参考 Intel/AMD、Microsoft、Linux 内核、UEFI 等一手资料，并注明适用范围。

### 3.3 渐进实现：每次增加一个能解释、能验证的能力

- 先建立小而完整的 8086 机器，再升级为 PC/AT、386、486。
- 以能力依赖为教学顺序，以 CPU 演进为阶段；不机械重复各代 CPU 的全部指令和外设。
- 从真实 8086 指令子集开始，避免先引入与最终架构无关的玩具指令集。
- 每章明确“上一章已有什么、本章增加什么、尚未实现什么”。
- 核心代码展示采用“原理伪代码 → 本章可运行实现 → 完整项目实现”的层次。
- 先解释正确的简单实现，再引入缓存、快路径、事件调度和真机兼容细节。
- 教学代码优先追求可理解性和正确性，而不是宿主执行性能。最初的取指循环可只表达读取操作码、推进 IP、执行和停机；分段、前缀、异常、中断和时间模型随章节逐步加入，未加入部分明确说明。
- 取指快路径、段访问缓存、TLB 快路径和事件驱动优化应在相关机制讲清后再介绍，不为保持工程实现的结构而提前增加复杂度。
- 教学代码与最终工程代码可以采用完全不同的结构；对照标准是双方在约定范围内实现相同的、已定义的行为，不是源码形状或内部执行步骤相同。
- 既要能够观察已完成机器，也要能够亲手实现机器；两种活动不能相互替代。

### 3.4 实验闭环：预测、运行、观察、破坏、验证

- 每章至少一个正常实验；适合的章节至少一个能够说明因果关系的失败实验。
- 实验必须有具体预期结果，不能只描述“看到程序运行成功”。
- 引导读者先预测结果，再检查状态变化和实际执行路径。
- 错误、未实现能力和不满足的前置条件必须明确呈现，不静默补装或用完整项目代跑。

## 5. 统一章节模板

文字稿应写成能够连续阅读的讲解，而不只是实验操作说明或代码摘要。保留必要的代码、表格和断言，并在其前后补齐问题来源、概念衔接、设计理由、推理过程和常见误解。先解释输入和状态之间的因果关系，再给公式与代码；对于新术语，说明它在当前机器中解决什么问题、由谁提供、与读者可能熟悉的概念有什么区别。

扩写以帮助理解为目标，不以篇幅为目标。不要仅增加术语清单或重复结论，也不要用类比代替真实机制；用具体的正常与边界例子展开推理，并明确类比及简化模型的适用边界。读者应当能够在不运行代码时先推导一次操作，再用已有实验验证。

1. 本章问题及与上一章的关系。
2. 前置知识、本章已有与新增能力。
3. 职责地图：机制、参数、数据、代码、策略、宿主替代的来源。
4. 真实硬件原理：状态、寄存器、接口、数据流。
5. 逐步实现：必要代码、设计理由、状态不变量与状态转换契约，以及对应测试断言。
6. 完整追踪一次操作：从输入到结果，逐步标注执行者。
7. 正常实验与失败实验：预测、运行、观察、解释。
8. 对照当前项目：完整实现额外解决哪些兼容性和性能问题。
9. 古今对照：今天的地位、用途变化、替代机制、适用范围。
10. 验收：固定测试断言、实验结果、练习、源码版本、下一章要解决的问题。

重要代码可配简短说明框，标明模拟对象、输入来源、固定规则、软件配置、输出和不负责的工作。不要求逐行重复职责标签。

### 5.1 贯穿案例：输出、存储和输入

| 案例 | 覆盖内容 | 使用方式 |
|---|---|---|
| 输出一个字符 | CPU、显存、BIOS、DOS、操作系统接口 | 主要贯穿案例 |
| 读取一个扇区 | 控制器、中断、DMA、IDE、BIOS、驱动、文件系统 | 存储相关章节的辅助案例 |
| 响应一次按键 | 键盘控制器、PIC、中断、缓冲区、应用程序 | 输入相关章节的辅助案例 |

三个案例共同展示输出、存储和输入的数据流，不要求每章重复三个案例，也不为覆盖案例而提前引入尚未讲述的能力。

“输出一个字符”依次对比：

1. 应用直接写显存。
2. 应用调用 BIOS INT 10h。
3. 应用调用 DOS INT 21h。
4. 保护模式/V86 下的访问、异常或服务转交。
5. 现代 Windows/Linux 中的库、系统接口、终端或图形系统、驱动和设备。

每次追问：字符是谁准备的，接口是谁定义的，代码是谁提供的，权限是谁检查的，最终动作由谁完成。现代路径应区分控制台、重定向、终端窗口与 GUI，不假装只有一条调用链。

“读取一个扇区”在相关章节对比：BIOS 服务与直接访问控制器、轮询与中断、软驱 DMA 与本书 ATA PIO 路径，以及真实系统驱动如何接管访问。文件系统负责确定需要哪些扇区并解释内容，不等于每次裸扇区读取都经过文件系统；这些路径也不必同时经过 DMA、IDE 和 BIOS。

“响应一次按键”追踪：外部按键 → 控制器状态/扫描码 → IRQ 请求 → PIC → CPU 转入处理程序 → 软件缓冲与字符解释 → 应用读取。区分硬件处理扫描码、固件/系统组织输入、应用消费输入，以及本项目宿主输入转换的边界。

### 5.2 每章固定的状态不变量与测试断言

每章应列出少量关键状态不变量，并对重要操作给出前置条件、状态转换后的结果和失败条件。持续成立的不变量与仅在操作完成后成立的契约要分开描述，不能用“最终有输出”代替关键中间状态的验证。

每项要求对应可执行测试断言，标明初始条件、检查时刻、预期状态及理由。断言依据本章定义的行为，不绑定私有字段布局、函数拆分或性能优化方式；时间相关要求使用明确的单位和容差。

例如 CALL/RET：

- 成功执行 CALL 后，按当前近/远调用形式、操作数宽度和堆栈规则，正确保存返回位置，并转入目标地址。
- 返回地址指向 CALL 之后的下一条指令，不是 CALL 自身；近返回恢复 IP，远返回还恢复 CS。
- 被调用代码正确平衡栈、遵守约定且 RET 不额外清理参数时，返回后的 SP 与调用前一致；带立即数的 RET 和参数清理由对应约定单独检查。

例如分页与缺页：

- 合法映射的地址转换结果符合页表及页内偏移，访问权限按当前模式和控制位检查。
- 不存在或不允许的访问产生正确的缺页异常，CR2、错误码和保存的故障返回位置符合该模式的规则。
- 处理程序修复映射并按需使缓存失效、返回故障位置后，原指令可以重新执行并得到预期结果。
- 不将所有指令的缺页都假定为完全无副作用；涉及部分完成的复杂指令，应单独声明测试范围和实现限制。

失败实验应对应明确的契约违反或故障条件，例如不平衡栈、错误页权限或遗漏缓存失效；使用受控程序验证原因，不能只以“运行失败”作为断言。

## 6. 实验体系：三个成果、一套素材

| 成果 | 职责 |
|---|---|
| 文字书 | 原理、职责、代码、古今对照和实验解释 |
| 完整项目的教学环境 | 在完整机器上观察、调试、修改和验证 |
| 逐章独立虚拟机 | 从零累积构建，下载、运行、修改、测试 |

实验程序、输入、预期结果、职责说明尽可能共享。两个运行对象可用薄适配层加载同一实验，不强求高级 UI 或内部数据结构完全一致。

## 7. 完整项目教学环境要求

### 7.1 入口与模式

- 用户可以选择独立教学入口，按篇、章和实验浏览。
- 内部复用现有直接调试、双机、磁盘启动能力，不复制一套完整执行引擎。
- 教学入口属于课程工作台；实验按需要选择执行方式，不强制全部落入现有模式一。
- 保持原有模式的行为和用途。教学功能是增加，不应无理由移除一般调试能力。
- 本章未需要的功能可以隐藏以减少干扰，但界面隐藏不等于核心尚未实现，应明确这是完整平台。

### 7.2 一个实验的最低描述

每个实验应具有稳定标识，并描述：

- 关联章节、目标、前置条件和使用的实现版本。
- CPU 型号、设备、固件、DOS/驱动安装状态。
- 汇编源码及必要机器码、装载地址、入口、初始寄存器和内存。
- 输入事件、介质、时序、停止条件、执行预算。
- 观察点：寄存器、地址、端口、向量、设备状态和执行片段。
- 预期结果：具体值、输出、异常、事件顺序或时间范围。
- 状态不变量与操作契约：初始条件、检查时刻、预期状态及对应的自动测试断言。
- 失败变体、故障解释和恢复方法。
- 职责说明与真实机制/模拟替代说明。

不得沿用完整项目的默认 BIOS/DOS 配置而不说明其提供者。依赖缺失应明确报告，不静默安装。

### 7.3 交互与过程观察

- 提供加载、运行、暂停、单步、重置、断点和必要状态观察。
- 能从章节直接定位实验，重置可回到已知初始条件；保护未保存修改。
- 展示真实执行产生的指令、端口、中断和地址转换记录，并可关联到相关代码与状态。
- 明确区分实际执行记录、原理示意图和教学解释；不以预设动画冒充真实轨迹。
- 对中断入口等可变数据，应展示当前目标和已知安装来源；未知来源明确写为未知，不猜测。
- 读者可以显式修改程序或状态完成失败实验；修改动作应可识别。
- 单步回退只在支持且语义可靠的场景提供；不支持时使用重新装载或快照恢复。

## 8. 逐章独立代码要求

### 8.1 累积而非裁剪

- 第 N 章源码只依赖截至本章已建立的能力，不引用未来章节源码。
- 每章是可独立构建运行的完整工程，不只是补丁、片段或最终机器的功能开关配置。
- 新章继承前面已经承诺的行为；必要变更须解释并更新相关实验。
- 不必实现全部指令和兼容怪癖；明确本章支持范围。
- 核心优先保持清楚、直接、可解释。与完整项目对照已定义的行为，不要求共享优化结构或达到运行完整操作系统的性能。
- 未实现能力明确报错，不静默忽略，不把执行转交完整项目。
- 最小宿主装载器、入口状态和教学便利须明确标注，不能冒充 BIOS 或 CPU 固有行为。

### 8.2 分发与版本

每章发布：

1. 完整源码下载，包含依赖清单、锁文件、构建运行说明和许可证。
2. 固定源码标签或等价不可变版本，以及与上一章的差异入口。
3. 可直接访问的浏览器演示和匹配的版本标识。
4. 本章实验、验收测试、能力清单和已知限制。

在线演示、Git 标签、完整源码包分别满足不同需求，不能互相替代。演示与源码必须来自同一固定版本。

独立代码应在不安装观察模块时正常执行；在不依赖原完整项目的情况下可运行。各章使用统一工具链，避免逐章引入无关框架。

### 8.3 提交历史的使用方式

现有历史用于寻找设计思路、故障原因和功能演进，不直接等同于章节顺序。功能、兼容修复、性能优化可以按教学依赖重新整理。

- 不需要复刻历史上的错误或不完整状态。
- 有价值的错误可以整理成失败实验。
- 不为每章复制一遍完整项目；优先用独立教学代码线的固定版本管理累积状态。
- 不修改现有历史来制造教学顺序。
- 最终使用独立仓库还是当前仓库的独立区域，待纵向样例完成后决定。

## 9. 核心、宿主和观察工具边界

依赖方向应为：

```text
演示界面 / 观察模块 / 实验脚本
                ↓
宿主适配与运行控制
                ↓
虚拟机核心
```

### 9.1 虚拟机核心

包含 CPU、内存、总线、设备状态机、虚拟时间、事件调度和本章必要的机器组成。固件映像属于被模拟机器；高层固件替代应单独说明。

- 不依赖 DOM、Monaco、Canvas、Web Audio、网页按钮和教学文案。
- 可由浏览器和无 UI 测试驱动。
- 核心只推进虚拟时间；不由 UI 刷新频率决定设备行为。
- 面向设备的外部输入和输出通过明确接口传递。

### 9.2 宿主适配与运行控制

负责浏览器调度、速度/暂停、输入转换、画面渲染、音频播放、介质接入和实验装载。

- 浏览器提供显示与声音的呈现，不替代客体应执行的设备操作。
- 控制器传输、文件系统解释、宿主文件浏览和客体系统文件服务是不同职责。
- 不把宿主随机性、真实时间或异步完成顺序隐式混入需要可重复的实验。

### 9.3 观察与调试

先实现可选模块即可，不预设插件市场、动态加载、第三方协议或复杂通用框架。

接口按本章需要逐步增长：

| 能力 | 要求 |
|---|---|
| 只读状态 | 查看寄存器、内存和设备，不产生客体可见副作用 |
| 可选记录 | 记录指令、端口、中断、地址转换等实际操作 |
| 调试控制 | 单步、暂停、断点；写入状态必须是显式操作 |

关键不变量：

- 某些端口读操作会清状态或消费数据，面板不能用正常端口读来刷新；应提供无副作用查看能力。
- 观察接口不可仅凭名称视为无副作用，须验证真实行为。
- 核心允许少量可选观测钩子；解释、面板和演示逻辑不放进核心。
- 没有订阅时不构造大量追踪数据；记录有界，必要时明确报告截断。
- 开关观察不改变机器结果、设备事件次序或虚拟时间。
- 卸载模块后释放订阅，不留下影响运行的回调。
- 不用不受控的核心对象引用作为公共观察接口；内部状态有明确、只读的查看边界。
- 不承诺在简单教学核心中提供完整系统回退；观察、记录、快照和回退分别设计。

## 10. 模拟边界与资料要求

每章及每个发布阶段明确标注：

- 本章承诺的行为。
- 已实现的真实机制。
- 高层替代和宿主便利。
- 未实现、不精确或未经验证的部分。

特别说明：

1. 项目主要是指令级模拟，不等于预取队列、总线引脚、电气特性或精确周期级还原。
2. 平均每步虚拟时钟模型不能用于测量真实指令延迟；REP 迭代和中断步骤也不应一概称为完整指令。
3. BIOS/DOS 高层陷阱、ROM 桩代码及真实端口访问路径应分别展示。
4. CPU 执行支持与汇编器语法支持分开描述。386/x87 实验提供可读源码和匹配机器码，必要时说明外部汇编工具。
5. 历史记录与完整快照的状态范围不同，不宣称任意模式切换或设备操作都可以完整后退。
6. 没有缓存、对齐检查等能力时，应明确其指令或控制位是兼容占位还是完整实现。
7. 真实软件能运行只是一类集成证据，不能证明全部架构行为或数值边界正确。
8. OS、驱动、磁盘映像和第三方源码遵守许可证；默认实验优先使用自写、可分发素材，受限软件由读者自行合法准备。

## 11. 验证与验收

### 11.1 每章最低验收

- 文稿明确职责地图、实现边界和现代对照。
- 本章完整工程可构建，浏览器演示可运行，版本与书中一致。
- 至少一个实验具有可检查结果，并通过自动测试或明确的人工验收。
- 本章关键状态不变量和操作契约有固定的自动测试断言；仅提供视觉效果或人工确认不能替代这些断言。
- 本章新增与修复行为有少量聚焦测试；前面章节的已承诺实验仍通过。
- 失败实验能稳定表现指定原因，能恢复初始环境。
- 缺失依赖、无效输入、未实现指令和预算耗尽可区分，不假装正常完成。
- 未安装观察模块仍可执行；安装后结果与虚拟时间不变。
- 章节、源码、实验和版本互相可定位。

### 11.2 两个运行对象的对照

可以用完整项目与章节核心执行同一实验，比较本章已定义的寄存器结果、内存修改、输出、异常和设备事件。

- 不要求内部结构、缓存、UI、未定义标志和计步方式相同。
- 时间实验须声明时钟模型、单位、容差和事件顺序。
- 完整项目不是唯一正确性来源；存在疑问时依据规范、定向测试和真机证据判断。
- 不为简化比较而在教学核心中引入未讲过的完整项目能力。

### 11.3 可重复性

- 固定必要的初始状态、输入、介质、RTC 时间和其他非确定因素。
- 定义停止条件、执行预算、等待状态与失败输出。
- 无介质或外部工具时，明确说明不可执行的实验，不伪造验收通过。
- 大型真机数据集和受限商业工具不是普通章节验收的默认前提；需要时单独列为扩展验证。
- 修改完整项目仍遵循其现有验证要求，按影响范围运行测试和构建。

## 13. 实施顺序

### 阶段一：第一条指令的纵向样例

完成一个真正闭环，而不是先搭通用课程框架：

1. 对应文字样稿与职责说明。
2. 不依赖完整项目的最小 CPU 工程。
3. 浏览器运行宿主和可拆卸寄存器观察模块。
4. 完整项目中对应实验及最小教学入口。
5. 共享实验、聚焦测试、源码版本和在线演示。

验收：能读懂、能运行、能观察、能显式修改、能解释结果；无观察模块也能正常执行。

### 阶段二：定时器与中断样例

验证异步设备、时间调度和多层职责链。重点覆盖 IRQ、PIC、CPU、处理程序、EOI、HLT 唤醒，以及遗漏 EOI 的失败实验。

验收：实际轨迹和职责标注一致；观察不影响虚拟时间；实验能够重复。

### 阶段三：分页与缺页样稿

验证复杂机制的讲述粒度与观察需求。可以先利用完整平台写样稿和实验；它不要求在第一阶段提前实现整套保护模式。

通过前三个样例确定章节粒度、源码展示方式、实验描述和最小观察接口，再稳定目录与发布组织。

### 阶段四：按依赖逐章扩展

从最小 8086 沿主线累积，不跳过前置能力。每章完成文字、教学实验、独立代码和验收后，再发布固定版本。

### 阶段五：专题与集成收官

加入复杂显卡、声音和其他选读专题，整理现代对照表、真实软件案例和完整书稿。

## 14. 待定事项及决策边界

以下事项尚未决定，不应在开发中默认为已获批准：

- 教学代码放在独立仓库、分支，还是当前仓库的独立区域。
- 书稿发布形式、站点结构和源码包组织。
- 教学实验描述格式，以及不同执行方式的具体适配接口。
- 观察模块是构建时可选导入，还是确有需求后增加动态加载。
- 现有调试 UI 与新观察工具共用到什么程度。
- 各复杂外设专题的篇幅、必读/选读划分。
- 单章支持的指令范围、时间精度和回退能力。

决策原则：以样例证明需要，优先简单方案；不提前设计插件生态、通用模拟框架或完整现代系统。涉及运行行为、格式兼容或明显扩大范围的选择，应先确认再实施。

## 15. 总体验收标准

最终读者应能够：
